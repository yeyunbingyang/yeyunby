# 1. 什么是大数据运维

**大数据**:

简单来说，就是指那些太大、太复杂，无法用传统的数据处理工具（如数据库）来管理和分析的数据。这些数据可以是从社交媒体、在线购物、传感器等多种来源产生的，通常具有**数据量大**、**种类多**、**更新快**等特点。比如，网上每一条评论、每一次点击、每一张图片都可能是大数据的一部分。

大数据存在的价值, 主要是用于解决**海量数据的存储**和**海量数据的计算**

**大数据运维**:

指针对大数据系统的运行和维护工作。由于大数据的处理和存储非常复杂，运维人员需要确保大数据平台的稳定性、安全性和高效性。大数据运维工作包括监控系统的健康、优化存储和处理能力、进行数据备份和恢复、保障数据安全等方面。

大数据运维主要是用于对大数据相关技术栈进行管理维护工作

# 2. 大数据开发的二个方向

## 2.1 离线开发

离线开发，顾名思义，就是数据处理和分析不是实时进行的，而是定时批量处理。通常，这种方式适用于处理大量历史数据或周期性数据，比如每天、每小时或每周处理一次数据。

**特点**:

- **数据积累**：首先收集一段时间的数据，再统一处理
- **处理方式**：批量处理，通常需要定时调度任务，数据量较大，处理过程不需要特别快
- **应用场景**：比如，每天晚上做一次大规模的用户行为分析，或者每周做一次销售数据分析

**技术**：离线开发通常使用像**Hadoop**、**Spark**这种批处理框架

**优点**:

- 适合处理大量历史数据，效率较高
- 不要求实时响应，处理可以集中进行

**缺点**:

- 数据延迟，分析结果不能马上看到，通常需要等待一定时间

## 2.2 实时开发

实时开发是指数据的处理和分析几乎是**实时**进行的。也就是说，数据一产生，就立即进行处理和分析，并给出实时结果。

**特点：**

- **即时处理**：数据流动到系统后，立刻开始处理，几乎没有延迟。
- **处理方式**：实时流处理，不是批量处理。
- **应用场景**：例如，金融市场的实时监控，或者社交媒体上实时分析用户情绪。

**技术**：实时开发一般使用像**Apache Kafka**、**Apache Flink**等流处理框架。

**优点**：

- 可以快速响应用户的需求或系统的变化。
- 适合需要快速反馈和实时决策的场景。

**缺点**：

- 需要处理大量并发的实时数据，对系统性能和稳定性要求高。
- 实现复杂，维护难度大。

## 4.1 Hadoop平台建设

### 4.1.1 Hadoop介绍

Hadoop是Apache旗下的一个用java语言实现开源软件框架，是一个开发和运行处理大规模数据的软件平台。允许使用简单的编程模型在大量计算机集群上对大型数据集进行分布式处理。

Hadoop基于Java实现 => JDK

Hadoop属于Apache基金会（ASF）下的一个开源框架 => 开源 + 免费

Hadoop主要是对大数据集（数据量比较大 => 适合处理GB级别以上数据集）进行分布式（多台机器）处理。

![[0dcb0558a2.png]]

① 狭义上说，Hadoop指Apache这款开源框架，它的核心组件有：

- HDFS（分布式文件系统）：解决海量数据存储
- YARN（作业调度和集群资源管理的框架）：解决资源任务调度
- MAPREDUCE（分布式运算编程框架）：解决海量数据计算

Map ：分，把大数据分解为多个部分，每个部分单独计算

Reduce：合，把每一个Map计算的结果进行合并汇总得出最终计算结论

![[d715fadd90.png]]

② 广义上来说，Hadoop通常是指一个更广泛的概念——Hadoop生态圈。

![[7277fa1241.png]]

当下的Hadoop已经成长为一个庞大的体系，随着生态系统的成长，新出现的项目越来越多，其中不乏一些非Apache主管的项目，这些项目对HADOOP是很好的补充或者更高层的抽象。

什么是元数据?

- 概念: 描述数据的数据被称为元数据

```
生活中:图书馆        
    如何能够在图书馆中快速找到一本书呢?  对于一本书记录 位置信息(第几层, 那个栏目, 那个书架...)
    而这些信息都是在描述这本书, 此时认为这些数据就是书元数据信息

文件系统: windows文件
    如何确定某一个文件呢? 首先确定文件在那个盘符下, 在那个目录下面, 文件叫什么名字, 文件的类型, 文件的大小, 文件的创建修改数据, 文件所属那个用户....  这些数据都是在描述一个文件中内容, 此时认为这些数据都是描述文件的数据, 称为元数据
    场景: 当你拷贝一个特别大的文件的时候, 速度比较慢的, 但是如果将这个我这个删除 速度相当之快 (底层删除的就是元数据)
```

### 4.1.3 zookeeper介绍

zookeeper: 动物园管理员

zookeeper是apache基金会旗下的一款**开源免费**的软件,主要用来解决分布式集群中应用系统的**一致性**问题。

ZooKeeper本质上是一个**小文件存储系统** , 可以通过zookeeper提供的一些特有功能(节点类型 + watch机制), 对集群进行管理操作

注意:

zookeeper并不是直接对集群进行管理, 只是提供了一些功能, 其他的软件可以基于zookeeper提供这样的功能, 从而达到对管理集群的作用,是否需要使用zookeeper来对集群进行管理, 取决于软件架构选择

zookeeper的集群架构:

```
leader:    zookeeper中主节点
     1) 管理从节点
     2) 主要负责对zookeeper的事务(增 删 改)操作
     3) 将读取的请求转发给从节点

follower: zookeeper中从节点
     1) 与主节点保持通信, 从主节点同步数据, 保证数据一致性
     2) 负责数据(非事务)读取操作
     3) 负责将事务操作转发给主节点
     4) 参与主节点投票
 Observer: 观察者(一般不使用)
     目的: 提升zookeeper读取数据性能(参与非事务操作)
     没有投票权
```

![[caa29c34a8.png]]

**节点类型:**

```
在zookeeper中节点类型主要提供四种类型(二种): 
永久节点
    永久非序列化(非顺序)节点: 简称 永久节点  (PERSISTENT)
    永久序列化(顺序)节点  (PERSISTENT_SEQUENTIAL)
    特点: 
        节点构建不依赖与会话, 会话的开启和关闭, 对永久节点没有任何影响
        除非显现执行删除操作, 才会将永久节点删除, 否则永久节点一直存在
        在永久节点下, 可以构建子节点

临时会话节点
    临时会话非序列化节点 : 简称 临时节点 (EPHEMERAL)
    临时会话序列化(顺序)节点 (EPHEMERAL_SEQUENTIAL)
    特点:
        会话结束，临时节点将被自动删除
        临时节点不允许构建子节点

序列化:
    给指定节点创建序列化节点, 如果当下没有任何子节点, 序号会从 十个 0开始(默认值), 每一次在这个目录创建节点, 都会自增+1(不管同名还是不同名) , 如果在目录建立非序列化节点, 起始内部也在+1 只不过看不到而已

目的: 保证记录同名称节点创建顺序, 保证唯一性

注意:
    不管是哪种类型的节点, 在创建节点之初 就已经确定了
```

zookeeper的watch机制:

```
在zookeeper中, 我们可以对其中的某个节点进行监听操作,  当这个节点发生一些状态时, zookeeper会通知监听者, 这就是zookeeper的watcher监听机制

可以监听的类型: 对节点和子节点的监听
    节点的创建、修改、删除操作
    子节点的创建、修改、删除操作
```

### 4.1.5 datanode的节点上下架

在Hadoop高可用（HA）集群中动态上架（新增）和下架（退役）DataNode的完整流程如下：

#### **4.1.5.1 动态上架DataNode（新增节点）**

##### **准备新节点**

- 1- 准备一个新的服务器,并且做好初始化
- 2- 安装好Hadoop, 并且启动datanode 和 nodeManager

- 2.1 将其他节点的hadoop和JDK拷贝一份发送给新节点, 并且设置软连接和环境变量
- 2.2 单独启动:

- hadoop-daemon.sh start datanode
- yarn-daemon.sh start nodemanager

- 注意:

- yarn集群直接就支持动态增加从节点, 只要增加了, 就自动有了
- hdfs集群直接就支持动态增加从节点, 只要增加了, 就自动有了 [建议依然按照配置要求进行配置并刷新]

##### **添加新节点到HDFS Include列表**

- **编辑NameNode的**`hdfs-site.xml`：

```
<property>
  <name>dfs.hosts</name>
  <value>/opt/hadoop/etc/hadoop/dfs_include.txt</value>
</property>
```

- **更新**`dfs_include.txt`文件：

```
# 在NameNode节点执行，添加新节点主机名
echo "new-datanode-hostname" >> /opt/hadoop/etc/hadoop/dfs_include.txt

注意: 一旦有了该文件,需要将所有的datanode节点全部加入, 然后再加入新的节点即可
```

- **动态刷新配置**：

```
hdfs dfsadmin -refreshNodes
```

##### **启动DataNode服务**

- **在新节点启动DataNode**：

```
hadoop-daemon.sh start datanode
```

- **启动NodeManager（若需参与YARN计算）**：

```
yarn-daemon.sh start nodemanager
```

##### **验证新节点**

- **查看HDFS节点状态**：

```
hdfs dfsadmin -report
```

- **查看YARN节点状态**：

```
yarn node -list
```

#### **4.1.5.2 动态下架DataNode（退役节点）**

##### **安全退役节点**

- **编辑NameNode的**`hdfs-site.xml`：

```
<property>
  <name>dfs.hosts.exclude</name>
  <value>/opt/hadoop/etc/hadoop/dfs_exclude.txt</value>
</property>
```

- **更新**`dfs_exclude.txt`文件：

```
# 在NameNode节点执行，添加待退役节点主机名
echo "old-datanode-hostname" >> /opt/hadoop/etc/hadoop/dfs_exclude.txt
```

- **动态刷新配置**：

```
hdfs dfsadmin -refreshNodes
```

##### **监控块复制进度**

- **查看退役状态**：

```
hdfs dfsadmin -report | grep "Decommission Status"
```

- 等待状态变为 `Decommissioned`（所有数据块已复制到其他节点）。

##### **停止服务并移除节点**

- **停止DataNode服务**：

```
# 在待退役节点执行
hadoop-daemon.sh stop datanode
```

- **停止NodeManager服务**：

```
yarn-daemon.sh stop nodemanager
```

- **从**`dfs_include.txt`中移除节点：

```
sed -i '/old-datanode-hostname/d' /opt/hadoop/etc/hadoop/dfs_include.txt
hdfs dfsadmin -refreshNodes
```

#### **4.1.5.3 自动化管理（可选）**

##### **使用脚本批量操作**

- **上架脚本示例**：

```
#!/bin/bash
NEW_NODE="new-datanode-hostname"
echo $NEW_NODE >> /path/to/dfs_include.txt
hdfs dfsadmin -refreshNodes
ssh $NEW_NODE "hadoop-daemon.sh start datanode"
```

##### **使用Ansible/Puppet工具**

- **Ansible Playbook片段**：

```
- name: Add new DataNode
  hosts: namenode
  tasks:
    - lineinfile:
        path: /path/to/dfs_include.txt
        line: "{{ new_node_hostname }}"
    - command: hdfs dfsadmin -refreshNodes

- name: Start DataNode
  hosts: new_node_hostname
  tasks:
    - service:
        name: hadoop-datanode
        state: started
```

#### **4.1.5.4注意事项**

1. **副本数要求**：

2. 确保退役前HDFS的副本数（`dfs.replication`）≥2，否则可能导致数据丢失。

3. **监控磁盘和网络**：

4. 退役期间HDFS会触发大量数据复制，需监控磁盘I/O和网络带宽。

5. **错误处理**：

6. 若节点无法退役，检查日志（`$HADOOP_HOME/logs/hadoop-*-datanode-*.log`）中的错误信息。

7. **NameNode HA兼容性**：

8. 在HA模式下，需在所有NameNode节点同步`dfs_include.txt`和`dfs_exclude.txt`文件。

## 4.3 Sqoop数据采集组件搭建

### 4.3.1 什么是SQOOP

Apache Sqoop是在Hadoop生态体系和RDBMS体系之间传送数据的一种工具。来自于Apache软件基金会提供。

Sqoop工作机制是将导入或导出命令翻译成mapreduce程序来实现。在翻译出的mapreduce中主要是对inputformat和outputformat进行定制。

Hadoop生态系统包括：HDFS、Hive、Hbase等

RDBMS体系包括：Mysql、Oracle、DB2等

## 5.1 消息队列的基本介绍

### 5.1.1 消息队列产生的背景

消息队列，英文名：Message Queue，经常缩写为MQ。从字面上来理解，消息队列是一种用来存储消息的队列。

```
消息(message): 指的是数据, 只不过这个数据存在一定流动状态
队列(queue): 指的容器, 可以存储数据, 只不过这个容器具备 FIFO(先进先出)特性

消息队列: 指的数据在一个容器中, 从容器中一端传递到另一端的过程
```

![[18b6d19d2a.png]]

```
思考: 公共容器需要具备什么特点呢?
    1- 公共性 (各个程序都可以与之对接)
    2- FIFO特性: 先进先出
    3- 具备高效的并发能力
    4- 具备一定的容错能力, 比如 支持重新读取消息方案

    目前希望能够有一些方案, 能够满足以上的所有的特性, 为了解决这类情况, 在市场上专门提供了一些相关的产品来处理以上的特性. 而这类产品其实就是消息队列的相关产品, 而且这些产品的名称. 大多以MQ的名称结尾
        
    常见的消息队列产品:  activeMQ rabbitMQ  rocketMQ Kafka Pulsar ....
```

### 5.1.2 常见的消息队列的产品

```
activeMQ : 出现时期比较早的一款消息队列的中间件产品, 在早期使用人群是非常多, 目前整个社区活跃度严重下降, 使用人群基本很少
rabbitMQ : 此款是目前使用人群比较多的一款消息队列的中间件的产品,  社区活跃度比较高, 主要是应用传统业务领域中
rocketMQ : 是阿里推出的一款消息队列的中间件的产品, 目前主要是在阿里系环境中使用, 目前支持的客户端比较少, 主要是Java中应用较多
Kafka :   Apache旗下的顶级开源消息, 是一款消息队列的中间件产品 项目来源于 领英 , 是大数据体系中目前为止最为常用的一款消息队列的产品
Pulsar :  目前是由StreamNative公司维护的一款云原生的消息队列的产品,  目前已经是Apache旗下顶级的开源项目 近一两年中新起的消息中间件的产品
```

### 5.1.3 消息队列的作用

消息队列的作用:

- 1- 应用解耦合
- 2- 异步处理
- 3- 限流削峰: 应用在高并发的场景中, 通过消息队列对接高并发的请求, 提高系统稳定性, 降低硬件成本 (秒杀场景)
- 4- 消息驱动系统

### 5.1.4 消息队列的两种消息模型

在Java中, 为了能够集成消息队列的产品, 专门提供了一个消息队列的协议: JMS(Java Message Server) java消息服务

消息队列中两个角色: 生产者(producer) 消费者(consumer)

在JMS规范中, 专门规定了两种消息消费模型:

- 1- 点对点消费模型: 指的一条消息最终只能被一个消费者所消费
- 2- 发布订阅消费模型: 指的一条消息最终被多个消费者所消费

## 5.2 Kafka的简介

Kafka 是一个**分布式流处理平台**，最初由 LinkedIn 开发，现由 Apache 软件基金会维护。它被设计用来处理大规模实时数据流，提供高吞吐量、低延迟的消息传递能力。

**核心功能**：

- **发布-订阅消息系统**：生产者（Producers）向主题（Topics）发布消息，消费者（Consumers）订阅并处理这些消息。
- **容错与高可用性**：通过数据复制和分布式架构，确保数据不丢失，系统持续运行。
- **可扩展性**：支持水平扩展，能轻松处理 PB 级数据。

**其价值所在:**

- **大规模数据处理**：通常需要处理海量数据，Kafka 的高吞吐量和低延迟特性使其成为理想工具。
- **实时数据流**：支持实时处理，适用于日志分析、系统监控、事件驱动架构等场景。
- **解耦系统**：通过消息队列解耦生产者和消费者，提升系统灵活性和可维护性。
- **云原生支持**：与 AWS、Azure、GCP 等云服务无缝集成。

![[c13ef224af.png]]

## 5.3 Kafka的架构

![[6230515cd9.png]]

**Topics（主题）**：

- 消息的分类单元，类似于数据库中的表。
- 每个 Topic 可分为多个分区（Partitions），支持并行处理。

**Partitions（分区）**：

- Topic 的子集，数据在分区内有序存储。
- 分区分布在不同 Broker 上，实现负载均衡。

**Brokers（代理）**：

- Kafka 集群中的服务器节点，负责存储和处理消息。
- 每个 Broker 管理多个分区的 Leader 或 Follower 副本。

**Producers（生产者）**：

- 向 Topics 发送消息的客户端。
- 可指定消息发送到哪个分区。

**Consumers（消费者）**：

- 从 Topics 读取消息的客户端。
- 通过消费者组（Consumer Group）实现多个消费者并行处理。

KRaft 模式的特点

- **去中心化**：KRaft 模式移除了对 Zookeeper 的依赖，Kafka 自身管理集群的元数据。
- **整合角色**：在 KRaft 模式下，节点可以同时承担 `broker` 和 `controller` 的角色，也可以单独承担某一个角色。整合这两个角色可以简化集群的部署和管理。

        领导者选举：当某个分区的领导者故障时，controller 负责选择新的领导者。
        集群状态监控：监控整个集群的状态，并协调各节点之间的操作。
        配额和限流管理：可能负责一些高级功能，例如资源配额和限流。

## 5.5 性能基准测试

Kafka的基准测试, 主要是用于测试Kafka集群的吞吐量, 每秒钟最大可以生产多少条数据, 以及每秒钟最大可以消费多少条数据

在测试过程中, 由于吞吐量受Topic的分片和副本的数据影响非常大, 需要在测试的过程中, 需要基于不同的分片和副本的情况来进行测试操作, 以便于测试出一个最精确的值

影响集群吞吐量的因素:

- 1- 节点的数量: 决定了同时可以有多少个服务器一起干活
- 2- topic的分片数量: 决定并行度
- 3- topic的每个分片副本数量

```
推荐: 并行度是节点数量的2~3倍  可以达到最优的性能

副本越多, 越会影响性能, 建议是2~3为最佳
```

## 5.7. Kafka的核心原理

### 5.7.1 Topic的分片和副本机制

分片有什么用呢?

```
解决单台节点容量有限的问题, 当然节点变多了, 自然整个效率也会提升, 吞吐量也会提升

通过分片, 可以将一个大的容器拆解为多个小的容器 分布在不同的节点上, 从而实现, 让多个来一起存储数据, 实现分布式存储

分片的数量有没有限制?  没有限制 , 与节点的数量是没有关系的   分片数量不会超过总节点数量的3倍
```

副本有什么用呢?

```
提高数据的可靠性, 副本越多, 数据越可靠, 但是数据冗余程度越高

副本数量是否有限制呢? 有限制, 最多和节点的数量是相等的, 但是一般构建1~3之间
```

### 5.7.2 Kafka如何保证消息不丢失

#### 5.7.2.1 生产端如何保证消息不丢失

![[af2ee624a9.png]]

```
生产端是如何保证数据不丢失呢?
方案: 当生产者生产数据到Broker端后, Broker端应该给予确认响应(ack)

ACK确认机制, 主要有三种策略方案,分别为 0  1  -1(ALL)

0: 生产者只管将数据生产到Broker端, 不等待(不接收)Broker端返回的ack信息

1: 生产者将数据生产到Broker端, 需要等待(接收)Broker端Topic的对应分片上的主副本接收到消息后, 即认为消息发送成功了

-1(ALL): 生产者将数据生产到Broker端, 需要等待(接收)broker端Topic的对应分片上所有的副本都接收到消息, 即认为消息发送成功了

安全级别:    -1 > 1 > 0

效率级别:    0 > 1 > -1

生产中, 一般使用那种策略呢?  
    根据消息重要情况以及生成和消费速率来选择对应的级别
    一般来说: 重要程度越高的,安全级别越高, 速率越快的, 优先保证安全性, 在此基础上提升效率,两者平衡
```

相关的思考点:

```
1- 目前生产者发送一条数据到Broker. Broker给予一次响应, 如果Broker端迟迟没有给予响应, 怎么办?

答:  先等待, 然后重试, 最后报错, 先等待一段时间, 当超时后, 然后触发重试策略, 进行重试操作, 当重试依然没有响应, 最后程序报错, 停止发送

2- 生产者发送一条消息, Broker就要给予一次响应, 那么这样是否会占用更多的带宽呢? 如果占用, 如何解决呢?

答:  肯定会影响的, 可以引入缓存池, 生产者在生产数据的时候, 底层先将其放置到一个缓存池, 当池子中消息数据达到一批数据大小后, 会专门有一个子线程, 触发执行, 将数据生产到Broker端, 此时Broker端只需要对这一批数据给予一次响应即可(异步发送)

3- 采用一批一批的发送, 如果Broker端又没有给予响应, 但是呢, 此时缓存池中数据已经满了,如何解决呢? 

答: 程序员可以选择直接清空缓存池或者不清空, 如果数据是可重复读, 直接报错清空即可, 后续重新读取数据即可, 如果数据是不可重复读, 可以提前设置处理方案, 将每一个消息提前先找一个容器进行备份存储, 自己维护数据, 当发送成功, 删除一部分数据, 如果出错, 重启后, 先从这个容器将剩余数据发送即可, 当然如果选择不清空, 那么就一直等待即可
```

相关的参数:

```
1- buffer.memory: 设置缓冲池子大小        
    默认值: 33554432(32M)

2- retries : 重试的次数        
    默认值: 2147483647        
    最终的重试策略一般取决于超时时间配置操作

3- batch.size : 表示一批数据大小  (一批数据 数据大小阈值)        
    默认值: 16384(16kb)
        
4- linger.ms: 每一批次间隔时间  (一批数据  时间阈值)        
    默认值: 0(毫秒)

5- delivery.timeout.ms : 总超时时间(等待时间)       
    默认值: 120000(120s)

6- request.timeout.ms: 每一次请求后超时时间(等待时间)       
    默认值: 30000(30s)
        
重试次数计算:  总超时 / 每一次请求超时 -1  (不含本身第一次请求,第一次属于正常请求,后续再次请求, 归为重试)


这些参数需要再kafka的核心配置文件中 进行配置 /opt/kafka3.8/config/server.properties
```

#### 5.7.2.2 Broker端如何保证数据不丢失

Broker可以将每个分片的副本数量设置为多个,提高数据的可靠性同时还需要生产端将ACK设置为 -1

#### 5.7.2.3 消费端如何保证数据不丢失

![[0bd0505397.png]]

流程:

```
1- 消费者首先会连接Kafka集群, 从Kafka集群获取消息数据

2- Kafka集群接收到请求后, 首先会根据group_id 查询上一次消费到了哪个消息偏移量

3- 如果没有找到消费者对应的偏移量信息, 默认从当前的位置开始消费数据, 之前的消息默认不处理

4- 如果找到了上一次消费的位置, 那么就从记录的消息偏移量位置继续消费数据即可

5- 消费者消费完数据后, 会把对应的消息的偏移量信息重新提交给Broker进行记录
```

思考点:

```
思考: 请求这种处理逻辑是否可以保证数据不丢失呢?

答: 一定是可以的,但是会存在重复消费的问题

思考: 请问消费者的偏移量信息是记录在哪里的呢?

答: 在kafka0.8x版本之前, 这个信息是记录在zookeeper集群上,在0.8x以后的版本中, 将此信息从zookeeper中迁移到Broker上, 通过一个topic来记录: __consumer_offsets

此Topic是有50个分片 1个副本

当然也正因为有重复消费的问题 导致Kafka在跟钱相关业务中, 使用不多, 或者在传统业务领域使用不多, 主要应用在大数据领域中
```

### 5.7.4 Kafka中生产者的数据分发策略

何为生产者的数据分发机制呢?

```
指的:  生产者在生产数据到达Broker的某一个topic上, 这个消息数据最终应该落入到那个分片的副本上, 这就是生产者的分发策略
```

思考: 你能想到的分发策略有那些呢?

```
1- Hash策略(支持的):  在发送数据时候, 会针对数据中key, 先计算其Hash值(整数类型,相同的key值对应hash一定是相同的), 接着将hash值和该topic的分区数量 进行求余计算, 余数为几, 那么就将这个数据存储到对应的分区上即可
    好处: 保证相同的key的消息数据, 都可以保存到同一个分区上
    弊端: 如果有大量的key值相同, 可能会导致数据倾斜问题(一个分区上数据 远远大于其他分区的数据)
2- 随机分发策略(在Python客户端支持, 但是在Java中不支持)
3- 轮询策略(在2.4版本以上,已更改为粘性分区策略,如果在2.4版本以下支持的, 但是不管轮询还是粘性仅在Java客户端支持, Python端不支持)
    表示: 挨个依次存入数据即可, 比如有五个分区,  假设有1号分区存储,  1  2  3 4 0 1 2 3 4 0....
    在新的版本中, 将轮询策略更换为粘性分区策略: 一旦选定了某一个分区, 在一定的时间范围内, 不在改变, 这一段时间内的数据全部存入该分区, 等待一段时间后, 下一个时间段切换到其他分区(随机的)
4- 指定分区的策略 (支持的)
5- 自定义分区策略 (支持的)
```

额外的点:

```
轮询分发 和 粘性分发策略 :  JAVA
    轮询策略: 在kakfa的老版本中存在的一种策略(2.4版本以下), 当生成数据时候, 只有Value没有key的时候,采用轮询
        优点:  可以保证每个分区拿到的数据量基本是一样的, 因为一个一个轮着进行发送
        
        弊端:  如果采用异步的方式, 意味着一批数据发送到broker端, 由于是轮询策略, 将这一批数据拆分为多个批次(与分片数量一致),分别写入到不同的分片中, 每个分片都要给予响应, 影响效率(重新分批以及多次ack响应)

    粘性分区策略: 在kafka的新版本中(2.4以上), 存在的一种分区策略,当生成数据时候, 只有Value没有key的时候,采用粘性分区
        优点: 在发送数据的时候, 首先会先随机的选择一个分区, 然后尽可能黏上这个分区, 将后续的数据全部发送给这一个分区,此操作在异步发送中, 效率比较高, 可以保证一批数据都在同一个分区上, 只需要给予一次响应, 也不要重新分批
        
        弊端: 如果生成批次非常快, 或者发送到broker上的非常快, 有可能导致大量的数据都发给了同一个分区上
```

### 5.7.5 Kafka的消费者负载均衡机制

![[f109b163ce.png]]

```
消费者的负载均衡的机制规定:       
    1- 在一个消费者组内, 消费者的数量最多和所监听的topic的分片数量是相等的, 如果有多余的消费者, 那么必然会出现某些消费者处于闲置的状态       
    2- 在一个消费者组内, topic的一个分片的数据, 只能被一个消费者所消费,不允许出现一个分片被组内的多个消费者所消费的情况, 但是一个消费者可以消费多个分区的数据
```

思考: 如何基于Kafka实现点对点的消息模型, 以及 发布订阅的消息模型:

```
点对点: 把监听这个topic的消费者全部放置到同一个消费者组内, 这样消息必然只能有一个消费者消费

发布订阅:  把监听这个topic的消费者放置不同的消费者组内, 这样消息就可以被多个消费者所消费了
```

## 5.8 配额限速

生产者和消费者以极高的速度生产/消费大量数据或产生请求，从而占用broker上的全部资源，造成网络IO饱和。有了配额（Quotas）就可以避免这些问题。Kafka支持配额管理，从而可以对Producer和Consumer的produce&fetch操作进行流量限制，防止个别业务压爆服务器。

**限制producer端速率**

为所有client id设置默认值，以下为所有producer程序设置其TPS不超过1MB/s，即1048576/s，命令如下：

```
bin/kafka-configs.sh --zookeeper node1.itcast.cn:2181 --alter --add-config 'producer_byte_rate=1048576' --entity-type clients --entity-default
```

运行基准测试，观察生产消息的速率

```
bin/kafka-producer-perf-test.sh --topic test --num-records 50000 --throughput -1 --record-size 1000 --producer-props bootstrap.servers=node1.itcast.cn:9092,node2.itcast.cn:9092,node3.itcast.cn:9092 acks=1
```

结果：

50000 records sent, 1108.156028 records/sec (1.06 MB/sec)

**限制consumer端速率**

对consumer限速与producer类似，只不过参数名不一样。

为指定的topic进行限速，以下为所有consumer程序设置topic速率不超过1MB/s，即1048576/s。命令如下：

```
bin/kafka-configs.sh --zookeeper node1.itcast.cn:2181 --alter --add-config 'consumer_byte_rate=1048576' --entity-type clients --entity-default
```

运行基准测试：

```
bin/kafka-consumer-perf-test.sh --broker-list node1.itcast.cn:9092,node2.itcast.cn:9092,node3.itcast.cn:9092 --topic test --fetch-size 1048576 --messages 50000
```

结果为：

MB.sec：1.0743

**取消Kafka的Quota配置**

使用以下命令，删除Kafka的Quota配置

```
bin/kafka-configs.sh --zookeeper node1.itcast.cn:2181 --alter --delete-config 'producer_byte_rate' --entity-type clients --entity-default
```

```
bin/kafka-configs.sh --zookeeper node1.itcast.cn:2181 --alter --delete-config 'consumer_byte_rate' --entity-type clients --entity-default
```

Apache DolphinScheduler是一个分布式、去中心化、易扩展的可视化DAG工作流任务调度系统

DAG: 有向无环图(执行流程, 有方向但是无返回)

官网地址: [https://dolphinscheduler.apache.org/zh-cn/](https://dolphinscheduler.apache.org/zh-cn/)

![[d20183e406.png]]

## 6.2 DS架构说明

![[18acce5502.png]]

```
MasterServer
    MasterServer采用分布式无中心设计理念，MasterServer主要负责 DAG 任务切分、任务提交监控，并同时监听其它MasterServer和WorkerServer的健康状态。 MasterServer服务启动时向Zookeeper注册临时节点，通过监听Zookeeper临时节点变化来进行容错处理。 MasterServer基于netty提供监听服务。

WorkerServer
    WorkerServer也采用分布式无中心设计理念，WorkerServer主要负责任务的执行和提供日志服务。 WorkerServer服务启动时向Zookeeper注册临时节点，并维持心跳。 WorkerServer基于netty提供监听服务。

ZooKeeper
    ZooKeeper服务，系统中的MasterServer和WorkerServer节点都通过ZooKeeper来进行集群管理和容错。另外系统还基于ZooKeeper进行事件监听和分布式锁。 我们也曾经基于Redis实现过队列，不过我们希望DolphinScheduler依赖到的组件尽量地少，所以最后还是去掉了Redis实现。

AlertServer
    提供告警服务，通过告警插件的方式实现丰富的告警手段。

ApiServer
    API接口层，主要负责处理前端UI层的请求。该服务统一提供RESTful api向外部提供请求服务。

UI
    系统的前端页面，提供系统的各种可视化操作界面。
    
    
    
架构讲解话术:
    通过UI进行工作流的配置操作, 配置完成后, 将其提交执行, 此时执行请求会被API服务接收到, 接收到后, 随机选择一台Master来完成任务的处理(DAG, 任务分配, 资源处理...)(底层最终是有对应schedule具体完成),完成分配后, 将对应执行的任务交给对应worker(从节点)来执行, worker对应有一个logger服务进行日志的记录, 在执行过程中, 通过logger实时查看执行日志, 当执行完成后, 通知Master, Master进行状态变更,同时告警服务实时监控状态, 一旦发现状态出现异常, 会立即根据所匹配的告警方案, 通知给相关的人员
```

## 8.3 Apache Flume 采集平台

### 8.3.1 Flume的基本介绍

Flume是Apache旗下一款开源免费, 专门用于进行数据采集的工具, 最早来源于cloudera公司, 后期将其贡献给Apache, 成为Apache顶级开源项目 Flume 采用Java 编写

官方网站: https://flume.apache.org/

Flume为了能够满足大部分采集场景, 提供各种针对不同的采集数据源和目的地的组件 , 以满足各种采集的场景

Flume在早期的版本中, 称为 Flume OG(1.X版本以前), 在新版本中称为Flume NG(1.x以后)

运行一个Flume的实例, 就是启动了一个Agent实例对象, 一般Agent由三个部分组成的

```
1- Source 组件: 数据源  用于读取数据源中数据, Flume为了支持从不同的数据源中读取数据, 提供多种Source组件
2- Channel组件: 数据管道 用于连接Source 和 Sink组件, 起到数据缓存的作用, 支持多种Channel方案, 一般主要使用内存管道 
3- Sink组件:  下沉组件 主要是用于将数据下沉到指定的目的地, 为了支持不同的下沉地,Flume提供多种Sink组件
```

数据从Source 到 Sink, 都是通过 event对象进行数据传输的, 一条数据就是一个event对象, 在event对象中, 除了可以放置本身数据以外, 还支持放置一些其他的描述信息数据, 默认只有数据本身

Flume一般是安装在数据采集的节点上

使用Flume 主要是配置Flume的采集配置文件,一般不需要写代码即可完成数据采集

Flume的使用帮助文档: https://flume.apache.org/releases/content/1.9.0/FlumeUserGuide.html

## 9.2 FineOps简介

FineOps运维平台是保障帆软应用稳定运行和全方位运维管理的解决方案，可以实现运维管理提效、实时监控预警应用状态和多项目管理统一等场景，确保业务正常运转。

背景说明:

```
企业在管理帆软应用（FineReport、FineBI）的过程中，常常会遇到一些痛点和挑战：
1）低效的运维流程：应用管理员运维经验不足，专业运维人员又无法深入解决应用问题，传统运维流程耗时耗力，导致企业运维效率低下，影响业务的正常运转。

3）多项目管理混乱：企业可能有多个项目运行，而这些项目由不同的部门或团队负责管理，导致版本不统一、部署环境各异，难以进行统一的运维管理。

因此帆软推出「运维平台」工具，帮助企业更好地解决以上问题。
```
