# Codex 使用指南

Codex 是 OpenAI 的编程 Agent，可以理解代码库、编辑文件、运行命令、执行测试、审查差异并协助完成 Git 工作流。它不只是代码补全工具，更适合承接具有明确交付结果的工程任务。

> [!abstract] 核心原则
> 给 Codex 一个可验证的目标、必要的上下文、清晰的权限边界和完成标准。不要只说“帮我改一下”，要说明改什么、不能动什么、怎样证明已经完成。

本文以 OpenAI 官方文档为事实基线，覆盖桌面应用、CLI、IDE 扩展和云端任务。产品入口、模型列表、套餐额度和实验功能会持续变化，涉及这些内容时应以文末官方页面为准。

## 一、先选择合适的使用入口

Codex 的多个入口共享核心能力，但适用场景不同。

| 入口 | 最适合的任务 | 特点 |
|---|---|---|
| Codex／ChatGPT 桌面应用 | 规划、并行任务、差异审查、跨应用协作 | 可视化管理任务，适合同时处理多个工作流 |
| Codex CLI | 本地仓库开发、终端操作、自动化脚本 | 离代码和命令最近，可交互使用，也可非交互执行 |
| IDE 扩展 | 围绕当前文件、选区和编辑器上下文编码 | 适合边阅读边修改，减少重复描述文件位置 |
| Codex Cloud | 远程、异步、可并行的仓库任务 | 在隔离云环境中执行，需要配置仓库和环境 |

选择建议：

- 日常本地开发优先使用 CLI 或 IDE 扩展。
- 需要规划、并行处理和集中审查时使用桌面应用。
- 需要把任务交给远程环境异步运行时使用 Codex Cloud。
- 需要在 CI 中运行时使用 `codex exec`、Codex GitHub Action 或 SDK。

> [!note] 登录方式的差异
> 桌面应用、CLI 和 IDE 扩展支持 ChatGPT 登录或 API Key。Codex Cloud 需要 ChatGPT 登录。API Key 按 OpenAI Platform 用量计费，部分依赖 ChatGPT 工作区或云服务的功能不可用。

## 二、安装、登录与自检

### 1. 安装 Codex CLI

Windows PowerShell 可使用官方安装脚本：

```powershell
irm https://chatgpt.com/codex/install.ps1 | iex
```

macOS 或 Linux 可使用：

```bash
curl -fsSL https://chatgpt.com/codex/install.sh | sh
```

已安装 Node.js 时也可以通过 npm 安装：

```bash
npm install --global @openai/codex
```

安装完成后检查版本和命令：

```bash
codex --version
codex --help
```

### 2. 登录

使用 ChatGPT 账号登录：

```bash
codex login
```

命令会打开浏览器完成认证。使用 API Key 时，应通过标准输入传递密钥，避免把密钥直接写进命令历史：

```bash
printenv OPENAI_API_KEY | codex login --with-api-key
```

PowerShell 示例：

```powershell
$env:OPENAI_API_KEY | codex login --with-api-key
```

检查或清除登录状态：

```bash
codex login status
codex logout
```

> [!warning] 密钥安全
> 不要把 API Key 写入笔记、源码、`AGENTS.md`、提示词或 Git 仓库。自动化场景应使用 CI 的 Secret 管理功能，并只在执行所需命令时注入。

### 3. 启动并确认工作目录

在仓库根目录启动：

```bash
cd /path/to/repository
codex
```

也可以显式指定目录：

```bash
codex --cd /path/to/repository
```

进入会话后运行 `/status`，确认：

- 当前工作目录正确。
- 当前模型和推理强度符合任务需要。
- 沙箱模式和审批策略符合预期。
- 可写目录没有超出任务范围。
- 剩余上下文足够完成当前任务。

## 三、完成第一个任务

一个可靠的任务描述通常包含五部分：

1. **目标**：最终要得到什么结果。
2. **范围**：允许修改哪些目录或文件。
3. **约束**：哪些内容不能改，必须遵循什么规范。
4. **验证**：需要运行哪些测试、检查或人工核验。
5. **交付**：希望看到摘要、差异、提交还是 PR。

示例：

```text
修复登录表单在请求失败后一直显示加载状态的问题。

范围：
- 只修改 src/features/login 和对应测试。
- 不调整公共请求封装，不升级依赖。

要求：
- 先复现并说明根因，再实施修复。
- 增加失败路径测试。
- 运行相关单元测试和类型检查。
- 最后汇报改动文件、验证结果和仍存在的风险。
```

这种写法能减少 Codex 猜测需求、扩大修改范围或只改代码不验证的情况。

### 推荐的交付闭环

```mermaid
flowchart LR
    A["说明目标和边界"] --> B["检查仓库与复现问题"]
    B --> C["提出方案或计划"]
    C --> D["实施最小修改"]
    D --> E["运行测试和检查"]
    E --> F["审查差异"]
    F --> G["提交或交付"]
```

每一步都应留下可核验的证据。对“完成”的判断以测试结果、运行输出、差异内容和实际产物为准。

## 四、提示词写法

### 1. 用结果描述任务

较弱的描述：

```text
看看这个项目，优化一下。
```

更有效的描述：

```text
把首页首次加载的 JavaScript 体积降低，目标是不改变现有功能和视觉效果。
先分析构成和主要来源，再提出不超过三个方案。
我确认方案后实施，并用构建产物对比修改前后的体积。
```

### 2. 明确允许自主决定的范围

```text
命名和局部实现细节可以自行决定。
涉及数据库结构、公共 API、依赖升级或删除文件时先征求确认。
```

### 3. 指定证据，不要求口头保证

```text
不要只说测试通过，请给出实际执行的命令、退出状态和关键结果。
如果无法运行某项验证，请说明阻塞原因，不要推测它应该能通过。
```

### 4. 让 Codex 先调查再修改

适合故障排查：

```text
先只读检查并定位根因，不要修改文件。
请给出复现路径、证据、影响范围和最小修复方案。
```

适合复杂项目：

```text
先进入计划模式，梳理需求、未知项、依赖关系和验证方法。
在计划获得确认前不要实施。
```

## 五、计划、执行与中途引导

复杂任务可使用 `/plan` 进入计划模式。计划应至少说明：

- 当前问题和目标状态。
- 需要检查的文件、模块和外部依赖。
- 实施步骤及其先后关系。
- 风险、未知项和需要确认的决策。
- 每一步的验证方式。

执行过程中发现新信息时，不必重开任务。直接补充约束或纠正方向，例如：

```text
新增信息：这个接口仍被旧版移动端使用，请保留向后兼容。
先重新评估现有方案，再继续修改。
```

需要尝试另一种方案而不干扰主线时，可使用 `/fork` 创建会话分支。只想临时追问一个问题时，可使用 `/side` 或 `/btw` 开启侧边对话。

长会话接近上下文上限时使用 `/compact`，让 Codex 压缩已有对话。压缩前应确保关键决策、未完成事项和验证结果已经明确写入会话或项目文档。

## 六、权限、审批与沙箱

Codex 的安全边界由两部分共同决定：

- **沙箱**决定命令能够读取、写入或访问什么。
- **审批策略**决定哪些操作需要用户确认。

CLI 常用沙箱模式：

| 模式 | 能力边界 | 适用场景 |
|---|---|---|
| `read-only` | 只读检查，不允许修改工作区 | 审计、调查、方案设计 |
| `workspace-write` | 可在工作区内写入，工作区外受限 | 日常开发的优先选择 |
| `danger-full-access` | 不受 Codex 沙箱约束 | 仅限已有外部隔离的可信环境 |

一次性指定模式：

```bash
codex --sandbox read-only
codex --sandbox workspace-write
```

会话中可用 `/permissions` 调整权限。执行高影响操作前应再次确认准确目标，包括：

- 删除、覆盖或批量移动文件。
- 推送分支、创建或合并 PR。
- 发布包、部署生产环境。
- 修改远程数据或向外部人员发送消息。
- 安装来源不明的脚本、插件或 MCP 服务。
- 访问工作区外的敏感目录。

> [!danger] 不建议的用法
> `--dangerously-bypass-approvals-and-sandbox` 会绕过审批和沙箱。只有在外部环境已经完成强隔离、任务输入可信且后果可恢复时才考虑使用。

## 七、用 AGENTS.md 固化项目规则

`AGENTS.md` 用于记录每次进入仓库都应遵守的持久规则，例如：

- 项目结构和关键入口。
- 安装、构建、测试和检查命令。
- 编码、命名和文档规范。
- 禁止修改的目录或生成文件。
- 完成任务前必须执行的验证。
- 代码审查关注点。

最小示例：

```markdown
# AGENTS.md

## 项目约束

- 所有用户可见文案使用中文。
- 不修改 generated/ 下的生成文件。
- 不在没有迁移脚本的情况下修改数据库结构。

## 验证

- 单元测试：npm test
- 类型检查：npm run typecheck
- 格式检查：npm run lint

## 交付

- 汇报实际运行的检查及结果。
- 未经明确要求不要提交或推送。
```

规则放置遵循“离目标文件越近，约束越具体”的原则：

- 全局个人规则放在 Codex Home 下的 `AGENTS.md`。
- 仓库通用规则放在仓库根目录。
- 子目录特有规则放在对应子目录的 `AGENTS.md`。
- 需要覆盖上层规则时使用 `AGENTS.override.md`。

使用 `/init` 可以生成项目 `AGENTS.md` 的初始结构。文件应保持简洁，只记录长期有效、经常重复的约束。一次性任务要求应留在当前提示词中。

## 八、CLI 常用工作流

### 1. 交互式会话

```bash
codex
codex "检查当前仓库并告诉我如何运行测试"
```

### 2. 恢复或分叉会话

```bash
codex resume
codex fork
```

### 3. 非交互执行

```bash
codex exec "运行测试并总结失败原因，不要修改文件"
```

`codex exec` 适合脚本和 CI。自动化任务应固定工作目录、权限、环境变量和输出要求，避免依赖交互式选择。

### 4. 代码审查

```bash
codex review
```

也可以在会话中使用 `/review`。审查结果仍需结合测试、静态检查和领域知识判断，不应把 Agent 审查当作唯一质量门槛。

### 5. 高频斜杠命令

| 命令 | 用途 |
|---|---|
| `/status` | 查看模型、权限、目录、上下文和会话状态 |
| `/model` | 选择当前账号可用的模型和推理强度 |
| `/permissions` | 调整当前会话的权限边界 |
| `/plan` | 进入计划模式 |
| `/compact` | 压缩长会话上下文 |
| `/diff` | 查看当前 Git 差异 |
| `/review` | 审查工作区修改 |
| `/mention` | 把指定文件或目录加入任务上下文 |
| `/skills` | 查看和调用 Skills |
| `/mcp` | 查看已连接的 MCP 服务与工具 |
| `/fork` | 从当前会话创建分支 |

命令会随版本和入口变化。遇到差异时，以 `/` 命令菜单、`codex --help` 和官方命令参考为准。

## 九、IDE 扩展

IDE 扩展适合围绕当前编辑器状态工作。它可以利用打开的文件、选区和编辑器上下文，减少手工复制代码。

推荐流程：

1. 在编辑器中打开仓库根目录。
2. 选中需要讨论或修改的代码。
3. 说明目标、边界和验证方式。
4. 审查 Codex 生成的差异。
5. 在集成终端中运行测试。
6. 使用 Git 面板确认没有无关修改。

如果 Codex 没有获得正确上下文，应显式附加文件或目录，而不是让它扫描整个仓库。CLI 中可使用 `/mention`，IDE 中可利用打开文件和选区上下文。

## 十、桌面应用、任务与 Worktree

桌面应用适合组织长任务、并行任务和差异审查。处理 Git 仓库时，可利用 Worktree 为不同任务创建相互隔离的工作目录，减少多个 Agent 同时修改同一工作树产生冲突。

适合使用 Worktree 的情况：

- 同时开发两个彼此独立的功能。
- 主线任务运行较久，需要并行调查另一个问题。
- 想尝试高风险方案但不污染当前工作树。
- 多个任务需要不同分支。

使用前确认：

- 当前目录确实是 Git 仓库。
- 未提交修改不会被另一个任务误用。
- 每个任务对应明确分支和工作目录。
- 合并前完成测试和冲突检查。

任务完成后先审查差异，再决定是否提交、推送或创建 PR。没有获得明确授权时，不应把“修改完成”自动扩展为“已发布到远程”。

## 十一、Cloud 环境

Codex Cloud 在远程隔离环境中执行仓库任务。使用前需要配置：

- GitHub 仓库访问。
- 基础容器镜像。
- 安装和启动脚本。
- 必要的环境变量与 Secret。
- 是否允许访问互联网，以及允许访问的域名。

云环境中的安装脚本在任务开始前运行。Secret 应只在初始化阶段使用，不要把它们写入日志或持久化文件。

适合 Cloud 的任务：

- 可独立验证的功能实现。
- 耗时测试和仓库调查。
- 多个相互独立的并行任务。
- GitHub PR 审查和修复。

不适合直接交给 Cloud 的任务：

- 依赖本机未同步文件或本地登录态。
- 必须操作桌面软件的任务。
- 缺少测试、验收标准或环境说明的模糊任务。

## 十二、Skills、Plugins 与 MCP

这三个概念解决不同问题：

| 机制 | 解决的问题 | 典型内容 |
|---|---|---|
| Skill | 如何重复执行一类任务 | `SKILL.md`、参考资料、脚本和资产 |
| Plugin | 如何安装和分发一组能力 | Skills、工具、MCP、Hooks、Apps 等组合 |
| MCP | 如何连接外部系统和实时数据 | 工具、资源、提示模板、认证配置 |

### 1. Skill

适合把稳定、重复的工作流程做成 Skill，例如：

- 发布前检查。
- 技术文档审计。
- 数据库迁移评审。
- 固定格式的周报生成。

全局 Skill 通常放在用户目录，仓库共享 Skill 放在 `.agents/skills/`。Codex 先读取 Skill 的名称和描述，匹配任务后再加载完整说明及所需资源。

详见 [[Codex-插件与技能系统]]。

### 2. Plugin

Plugin 是可安装、可分发的能力包。优先使用来源明确、维护状态良好并与当前 Codex 版本兼容的插件。安装前检查：

- 发布者和来源。
- 包含哪些 Skills、Hooks、MCP 或外部连接。
- 是否会执行脚本。
- 需要哪些权限和账号授权。
- 是否会向远程服务发送数据。

不要把“插件数量”或“必装插件清单”写成长期事实。插件目录、可用性和账号权限会变化，应在当前客户端的插件浏览器中确认。

### 3. MCP

MCP 用于连接 GitHub、Figma、文档服务、问题跟踪系统或内部工具。Codex 支持本地 STDIO 服务和远程 Streamable HTTP 服务。

添加一个 STDIO MCP 服务：

```bash
codex mcp add context7 -- npx -y @upstash/context7-mcp
```

常用检查：

```bash
codex mcp list
codex mcp --help
```

支持 OAuth 的服务可使用：

```bash
codex mcp login <server-name>
```

MCP 配置默认存放在 `~/.codex/config.toml`，可信项目也可以使用项目级 `.codex/config.toml`。桌面应用、CLI 和 IDE 扩展可共享同一 Codex Host 的 MCP 配置。

> [!warning] MCP 信任边界
> MCP 服务可能读取数据或执行外部操作。连接前应检查服务来源、授权范围、数据去向和工具是否具有写权限。对远程写操作继续采用最小权限和逐次确认。

## 十三、配置文件

Codex 的持久配置主要位于：

```text
~/.codex/config.toml
```

可信仓库可以使用项目级配置：

```text
.codex/config.toml
```

适合写入配置文件的内容：

- 默认模型和推理强度。
- 沙箱和审批策略。
- MCP 服务。
- Hooks。
- 功能开关。
- TUI 外观和通知。

一次性覆盖可使用 CLI 参数：

```bash
codex --sandbox read-only --ask-for-approval never
codex -c key=value
```

配置存在全局、项目、命令行和受管策略等多个层级。发现设置没有生效时，先检查配置优先级和组织策略，不要反复修改同一文件。

## 十四、记忆与长期上下文

Codex 的长期上下文应按用途分层：

- 当前任务临时要求放在提示词。
- 团队和仓库规则放在 `AGENTS.md`。
- 可复用流程放在 Skill。
- 个人或产品提供的记忆功能只保存适合跨会话复用的背景。

不要把自动记忆当作唯一事实来源。版本、接口、命令、价格和项目状态都可能变化，关键事实应回到仓库文件、官方文档或实时系统重新核验。

涉及隐私、账号、密钥、客户数据和内部敏感信息时，不应要求记忆保存。

## 十五、自动化任务

自动化适合周期性、可重复、结果可检查的任务，例如：

- 定期检查依赖更新。
- 每周汇总项目状态。
- 监测测试或构建失败。
- 定期审计文档中的过期内容。

自动化描述应包括：

```text
频率：
作用仓库或目录：
执行内容：
允许的修改范围：
验证方式：
结果输出位置：
失败时如何处理：
是否允许提交、推送或发送消息：
```

默认把自动化设计为只读或生成草稿。涉及提交、推送、部署、删除和外部消息时，应单独声明权限和审批条件。

## 十六、Git 与代码审查

推荐让 Codex 遵循以下顺序：

1. 执行前查看 `git status`。
2. 区分用户已有修改与当前任务修改。
3. 只编辑任务范围内的文件。
4. 运行测试、检查和构建。
5. 使用 `/diff` 或 `git diff` 审查内容。
6. 运行 `git diff --check` 检查格式问题。
7. 只暂存当前任务文件。
8. 获得明确授权后再提交、推送或创建 PR。

在存在大量未提交修改的仓库中，不要使用：

```bash
git add .
git reset --hard
git checkout -- .
```

这些命令可能混入、覆盖或删除用户尚未提交的工作。应按准确路径暂存，并在破坏性操作前核对目标。

## 十七、常见问题

### Codex 修改了过多文件

先停止继续实施，检查 `git diff --stat` 和 `git diff`。重新明确允许修改的目录、禁止项和最小方案，不要直接用破坏性 Git 命令回退整个工作树。

### Codex 一直请求权限

检查当前工作目录、沙箱模式、可写根目录和网络限制。应为具体命令或准确目录授予最小权限，不要为了省事直接开放完全访问。

### AGENTS.md 没有生效

检查：

- 文件名是否为 `AGENTS.md` 或 `AGENTS.override.md`。
- 启动 Codex 时的工作目录是否正确。
- 是否有更近目录的覆盖文件。
- 文件是否为空或过大。
- 是否需要新开会话重新加载规则。

可以让 Codex 执行：

```text
列出本次会话加载的所有指令来源，并按优先级说明。
```

### MCP 无法使用

依次检查：

1. `codex mcp list` 是否能看到服务。
2. 命令、URL 和环境变量是否正确。
3. OAuth 是否已完成。
4. 客户端或扩展是否已重启。
5. 当前账号、工作区或管理员策略是否允许。
6. 服务自身日志是否有启动或协议错误。

### 会话越来越偏离目标

先补充当前目标、已完成事项、禁止项和下一步。如果历史上下文已经混乱，使用 `/compact` 后再次确认摘要，或者创建新会话并提供干净的任务交接。

### 模型、命令或界面与本文不同

模型目录、功能成熟度和界面会持续更新。先查看 `/status`、当前客户端的命令菜单和官方文档，不要依据旧截图或第三方教程猜测。

## 十八、个人推荐工作模板

### 开始任务

```text
先读取仓库规则并检查 git status。
说明你理解的目标、范围、禁止项和完成标准。
如果发现用户已有修改，不要覆盖、恢复或混入当前任务。
```

### 实施任务

```text
先定位根因或建立事实基线，再做最小必要修改。
每完成一个阶段就运行对应验证。
遇到需要扩大范围、删除内容或改变公共接口的情况先说明原因。
```

### 完成交付

```text
请汇报：
1. 完成了什么。
2. 修改了哪些文件。
3. 实际运行了哪些验证及结果。
4. 还有哪些未验证项或风险。
5. 当前是否已暂存、提交或推送。
```
