## 阶段一：环境搭建（实操版）

### 1.1 模型配置

#### 🎯 思路

老师的设计意图：

- **researcher（调研员）** → 用 **DeepSeek**（便宜，推理能力强），因为调研需要大量搜索和阅读，token 消耗大
- **writer（撰稿员）** → 用 **Claude Sonnet 4.6**（写作质量高），因为文章质量是最终产出，值得用好模型
- **reviewer（审核员）** → 用 **Claude**，因为审核需要细致判断
- **publisher（发布员）** → 用哪个都行，只是执行 git 操作

> 💡 **老师建议**：如果无法使用 Claude（国内网络问题），**统一用 DeepSeek 也完全没问题**。可以用 v4 flash（便宜）和 v4 pro（更好）来区分档次。

#### 📋 步骤

**1. 配置 DeepSeek（必须）**

在 Hermes 的 provider 配置中添加 DeepSeek：

```bash
# 交互式配置
hermes provider add
# 选择 DeepSeek，填入 API Key 和 Base URL
```

或直接编辑 `~/.hermes/config.yaml`：

```yaml
providers:
  deepseek:
    api_key: sk-xxxxxxxxxxxxxxxxxxxx
    base_url: https://api.deepseek.com
```

**2. 配置 OpenRouter（可选，用于 Claude）**

```bash
# 1. 访问 https://openrouter.ai/
# 2. 用 GitHub 账号登录
# 3. 左侧 Keys → Create Key → 命名 "HERMES" → 复制
# 4. 在 Hermes 中添加 provider
hermes provider add
# 选择 OpenRouter，填入 Key
# 模型选: anthropic/claude-sonnet-4.6 (或 sonnet-4)
```

#### ⚠️ 踩坑

- **OpenRouter 的模型名要写全**：不是 "claude-sonnet"，而是 `anthropic/claude-sonnet-4.6`
- **Sonnet vs Opus**：老师推荐 Sonnet，因为 Opus "实在太贵了"，写一篇文章用 Sonnet 足够
- **国内网络**：如果 OpenRouter 访问慢，统一用 DeepSeek 即可

#### 💡 要点

- 模型配置好后，在创建 Profile 时可以用 `writer model` 交互式选择
- 不同 Profile 用不同模型是 Hermes 的核心优势，但不是必须的

### 1.2 创建四个 Profile

#### 🎯 思路

为什么分四个角色？

| 角色 | 职责 | 模型策略 | 工具限制 |
|------|------|---------|---------|
| researcher | 查文档、源码、网络资料 | 便宜模型（DeepSeek） | 仅 web + terminal |
| writer | 写文章 | 高质量模型（Claude） | 全开 + 写作 skill |
| reviewer | 审核文章 | 中等模型 | 全开 |
| publisher | 发布到 GitHub | 任意 | 仅 terminal + MCP |

**核心原则**：每个角色只做自己擅长的事，通过工具限制防止越界。

#### 📋 步骤

**1. 创建 researcher（调研员）**

```bash
# 创建 Profile
hermes profile create researcher --clone \
  --description "负责查阅文档、源码和网络资料，产出结构化研究结论。使用低成本模型。"

# 配置模型（交互式）
researcher model
# 选 15 (DeepSeek v4 flash)，回车确认 Key 和 Base URL

# 限制工具
researcher tools disable browser code_execution video_analyze

# 配置 SOUL.md（人格）
# ⚠️ 注意：SOUL.md 文件在 profile 目录下，需要手动找到路径
```

**2. 找到 SOUL.md 的正确路径**

```bash
# 方法一：直接搜索
find ~/.hermes/profiles/researcher -name "SOUL.md"

# 方法二：进入目录
cd ~/.hermes/profiles/researcher
# 用 VS Code 打开 SOUL.md
```

SOUL.md 内容（追加到文件末尾，保留原有内容）：

```markdown
# Researcher Soul
你是一名技术研究员。你的输出必须结构化：
1. 核心发现（一句话总结）
2. 关键信息点（bullet points）
3. 信息来源（URL + 一句话描述）
4. 建议方向（可选）

保持客观、精确。不要添加主观评价。
```

**3. 创建 writer（撰稿员）**

```bash
hermes profile create writer --clone \
  --description "负责把研究材料整理成清晰、连贯、有吸引力的技术文章。使用高质量模型。"

# 配置模型 - 选更好的
writer model
# 选 15 (DeepSeek v4 flash) 或 2 (v4 pro) 来区分档次
# 如果用 OpenRouter，选对应的 Claude 模型

# 安装写作 skill
writer skills install blogwatcher
# ⚠️ 注意：名称要写全，否则报错
# 正确：writer skills install "Blog Watcher"
```

**4. 创建 reviewer（审核员）**

```bash
hermes profile create reviewer --clone \
  --description "负责审查文档或代码变更，指出遗漏、错误和风险。"

# 模型保持默认（DeepSeek v4 flash）
# 交互式配置时一直回车即可保持默认
```

**5. 创建 publisher（发布员）**

```bash
hermes profile create publisher --clone \
  --description "负责将审核通过的文章发布到 GitHub Pages 博客仓库。"

# 限制工具 - 不能使用 web 搜索
publisher tools disable web browser
# 保留 terminal（git 操作）和 code_execution（可能用到）
```

#### ⚠️ 踩坑

- **SOUL.md 路径问题**：`cat > ~/.hermes/profiles/researcher/SOUL.md` 这种写法可能不准确，因为 profile 目录结构可能不同。**建议手动查找并编辑**。
- **writer skills install 名称问题**：技能名称需要写全，否则报 "not found"。先用 `writer skills list` 查看完整名称。
- **SOUL.md 的结束符号**：用 `cat >` 命令写入时可能会多出结束符号（如 `EOF`），需要手动清理。

#### 💡 要点

- 创建 Profile 后，**模型是默认继承当前 default 的**，需要用 `writer model` 交互式修改
- 如果不想交互式，也可以直接编辑 `~/.hermes/profiles/<name>/config.yaml`
- 工具限制不是强制的，但推荐做——防止 Agent 越界操作

### 1.3 微信网关配置

#### 🎯 思路

原笔记用 Telegram，老师替换为**微信**，因为国内使用更方便。核心流程：

```
微信消息 → Hermes Gateway → Hermes Agent → 处理 → 结果返回微信
```

#### 📋 步骤

**1. 安装/检测 Gateway**

```bash
hermes gateway setup
# 如果已安装，会检测到；如果未安装，按提示安装
```

**2. 配置微信**

```bash
hermes gateway setup
# 选 3 (微信)
# 是否使用二维码登录？Y
# 会生成一个链接，打开后扫码
```

**3. 扫码连接**

- 打开链接，显示二维码
- 用微信扫描
- 手机上点击「连接」
- 命令行显示连接成功，有 `account ID`

**4. 配置 allow_users**

这是**最容易忽略的步骤**。如果不配置，微信消息会被网关丢弃。

```bash
# 编辑 ~/.hermes/.env
# 拉到最下面，找到微信相关配置
```

在 `.env` 中：

```bash
# 方案一：允许所有用户（推荐首次测试）
WEIXIN_ALLOWED_USERS=true

# 方案二：指定用户（需要知道自己的微信 ID）
# 新版网关可能不显示用户 ID，用方案一更方便
WEIXIN_ALLOWED_USERS=wx_xxxxxxxxxxxxx
```

**5. 重启网关**

```bash
hermes gateway restart
# 或
hermes gateway stop && hermes gateway start
```

**6. 测试**

在微信中给机器人发 "你好"，应该能收到回复。

#### ⚠️ 踩坑

- **allow_users 不配置 → 消息被丢弃**：这是最常见的失败原因。网关会检查消息来源是否在允许列表中，不在则忽略。
- **新版网关不显示用户 ID**：旧版会显示 "你的 ID 是 xxx"，新版不显示了。此时用 `true` 或 `all` 允许所有用户。
- **重启命令变化**：新版可能用 `hermes gateway restart` 而不是 `hermes gateway start`。

#### 💡 要点

- 微信网关的配置信息会写入 `.env` 文件，**不要提交到 git**
- 如果换了微信号，需要重新扫码
- 微信有**消息推送频率限制**，频繁发长消息可能被限流

### 1.4 GitHub Token 配置与持久记忆

#### 🎯 思路

GitHub Token 用于 publisher 自动推送文章到仓库。持久记忆（Memory）让 Agent 记住博客的配置信息，**不需要每次重复告诉它**。

#### 📋 步骤

**1. 创建 GitHub Token**

```
GitHub 网页操作：
Settings → Developer settings → Personal access tokens → Tokens (classic)
→ Generate new token → 命名 "HERMES"
→ 勾选所有权限（反正自己用）
→ Create → 复制 ghp_xxxxxxxx 开头的 token
```

**2. 写入 env 文件**

编辑 `~/.hermes/.env`，找到 GitHub 相关配置：

```bash
# 原本是注释掉的，取消注释并填入 token
GITHUB_TOKEN=ghp_xxxxxxxxxxxxxxxxxxxxx
GITHUB_PERSONAL_ACCESS_TOKEN=ghp_xxxxxxxxxxxxxxxxxxxxx
```

> 两个都写上，因为 Hermes 可能用不同的变量名读取。

**3. 通过自然语言让 Agent 记住**

```bash
hermes chat -q "记住以下信息：我们的博客使用 GitHub Pages + Hugo 静态站点，仓库地址 github.com/yourname/blog，文章用 Markdown 格式，frontmatter 包含 title/date/tags/author 四个字段。发布流程是：新文章放在 content/posts/ 下，提交 PR，合并到 main 分支后自动部署。"
```

**4. 测试 Token**

```bash
# 在 publisher profile 中测试
publisher chat -q "我在 env 中配置了 GitHub Token，现在测试一下这个 Token 是否可以完成我的账号读取和推送功能"
```

#### ⚠️ 踩坑（重点！）

**Token 被 Hermes 自动隐藏**——这是老师演示中遇到的最大坑：

```
现象：Agent 拿到 Token 后，在日志中自动替换为 "****"
      导致后续 multi-agent 协作时 Token 传递失败
      多 Agent 之间只传递安全信息，Token 被过滤
      结果：Agent "左右脑互搏"——一会儿用 Token，一会儿隐藏
```

**解决方法**：

```bash
# 必须明确告诉 Agent：
"这个 Token 直接显示使用，不要再隐藏为暗码，以后也记住这一点"
```

老师原话：
> "你得明确的告诉他，不然的话呢，他这个 Token 作为一个环境变量在进行传递的时候，他总是把它给删掉。这个也是现在 Hermes 的一个问题，它这个安全等级就莫名其妙。"

#### 💡 要点

- 第一次跑复杂流程时，**建议在旁边盯着**，Token 问题会导致多 Agent 协作全部失败
- 跑通一次后，让 Agent 把流程记下来（Memory + Skill），后续就不会出同样的问题
- 如果不想用 GitHub，也可以让 publisher 发送到**邮箱**

## 阶段二：工作流设计（实操版）

### 2.1 创建看板与 Orchestrator

#### 🎯 思路

看板（Kanban）是整个工作流的**中枢神经系统**：

- 任务创建 → 看板
- 任务拆解 → 看板
- 任务执行 → 看板
- 任务状态跟踪 → 看板

Orchestrator（编排者）是**任务拆解的大脑**，负责把"写一篇文章"拆成调研→写作→审核→发布四个子任务。

#### 📋 步骤

**1. 创建博客看板**

```bash
hermes kanban boards create blog --name "技术博客工作板" --switch
hermes kanban init
```

**2. 创建 Orchestrator Profile**

```bash
hermes profile create orchestrator --clone \
  --description "Kanban 编排者。负责拆解文章选题、创建写作任务、指派 profile、建立依赖关系、汇总下游结果。"

# 限制工具 - 纯编排角色，不需要执行工具
orchestrator tools disable terminal file web browser code_execution

# 配置为自动拆解
hermes config set kanban.orchestrator_profile orchestrator
hermes config set kanban.auto_decompose true
```

#### ⚠️ 踩坑

- 创建 orchestrator 时，命令中的横杠可能被 shell 转义，需要处理
- 如果 `auto_decompose` 配置后不生效，检查 orchestrator 的模型是否可用

### 2.2 Cron 选题流水线

#### 🎯 思路

三阶段流水线设计：

```
每天早上 7:00   → 任务1：采集热点（HN + 知乎 AI/前端）
每天早上 7:30   → 任务2：筛选选题（从热点中挑 3 个）
每天早上 8:00   → 任务3：生成简报（大纲 + 核心观点 + 参考链接）
     ↓
  微信推送简报 → 负责人睡醒看到 → 挑感兴趣的发任务
```

**为什么这么设计？** 因为人不可能每天早上自己去刷新闻，让 Agent 帮你筛选好，你只做决策。

#### 📋 步骤

**1. 在 default profile 中进入对话**

```bash
hermes
```

**2. 让 Agent 创建三个 Cron 任务**

```
请帮我创建一组 Cron 任务，用于技术博客选题流水线：

1. 每天早上 7:00，收集 Hacker News 和知乎上的 AI/前端热门内容，
   用 web_search 工具获取，输出包含标题、链接、简要说明
2. 每天早上 7:30，读取任务 1 的最新输出，筛选 3 个最适合我们博客的选题，
   评估标准：技术深度、读者兴趣度、与已有文章的差异化
3. 每天早上 8:00，读取任务 2 的筛选结果，为每个选题生成一份简报，
   包含：文章大纲、核心观点、推荐参考链接、预估字数

所有任务结果投递到微信网关。
```

Agent 会自动创建三个任务并用 `context_from` 建立依赖链。

**3. 手动触发第一次执行（不等明天早上）**

```bash
# 让 Agent 立即执行三个任务
"现在依次执行任务 1、2、3"
```

**4. 调整简报字数（如果太长）**

微信有推送长度限制，简报太长会被截断或限流：

```
"限制定时任务生成简报的最终输出字数在 500 字以内"
```

**5. 减少微信推送频率（如果被限流）**

```
"因为微信会限制发送的消息，所以任务一采集热点和任务二筛选选题不再发送到微信"
```

这样只有任务三（简报）会推送到微信，每天一条，不会被限流。

#### ⚠️ 踩坑

- **微信推送限流**：如果三个任务都推微信，短时间内大量消息会被限流。**建议只让任务三（简报）推微信**。
- **简报太长**：Agent 默认可能生成上千字的简报，微信可能发不完整。**必须限制字数在 500 以内**。
- **第一次跑很慢**：老师演示时 "网络比较卡"，等了较长时间。第一次执行需要耐心等待。
- **查看运行结果**：如果微信没收到，可以在 `cronjob 管理` 中查看运行记录。

#### 💡 要点

- 三个任务通过 `context_from` 形成流水线：任务2 自动读取任务1 的输出，任务3 读取任务2 的输出
- 每天早上你醒来，微信上已经有筛选好的选题简报，直接挑一个感兴趣的让 Agent 写
- 如果某天不想发，直接忽略即可，不影响后续

## 阶段三：日常运行（实操版）

### 3.1 配置 SOUL.md 路由规则

#### 🎯 思路

当用户在微信上发 "写一篇关于 X 的文章" 时，Agent 需要**识别这是博客任务**，而不是自己回答。通过 SOUL.md 配置路由规则。

#### 📋 步骤

**编辑两个 SOUL.md 文件**（都要改，确保生效）：

**文件1：`~/.hermes/SOUL.md`（全局）**

```markdown
# Hermes Agent Soul

你是Hermes Agent, 你有一个完整的博客多智能体协作系统。

## 博客任务路由规则

当用户通过微信发送以下类型的请求时，**不要自己回答内容，不要自己写文章**，而是触发 Kanban Swarm 流程：

**触发关键词：**
- "写一篇关于...的文章/博客"
- "写一篇...深度文章"
- "写博客/写文章 主题"
- 任何明确的博客/文章创作请求

**执行步骤：**
1. 调用 `hermes kanban --board blog create "文章主题" --assignee orchestrator`
2. 回复用户："已创建博客写作任务，Orchestrator 正在拆解，稍后流程自动推进。"

**常规对话：**
非博客创作类的咨询、问候、闲聊，正常回答即可。
```

**文件2：`~/.hermes/profiles/default/SOUL.md`（default profile）**

同样内容也写一份。

#### ⚠️ 踩坑

- **必须重置会话才能加载新记忆**：修改 SOUL.md 后，在微信中发送 `/new` 或 `-new` 重置会话，否则 Agent 仍用旧记忆。
- **两个文件都要改**：老师演示时只改了一个，结果 Agent 没按预期走看板流程。

### 3.2 微信发起任务

配置完成后，在微信中发送：

```
写一篇关于 Hermes Agent Kanban Swarm 功能的深度文章，面向 AI 开发者
```

Agent 应该回复 "已创建博客写作任务"，然后自动触发看板流程。

#### 📋 验证

```bash
# 查看看板任务是否创建成功
hermes kanban list
# 应该能看到新创建的任务
```

### 3.3 看板 Swarm 自动执行

#### 🎯 思路

看板 Swarm 启动后，Orchestrator 自动拆解任务：

```
[写文章任务]
    ↓ Orchestrator 拆解
    ├── 任务A: 研究 Swarm 架构与设计理念 → researcher
    ├── 任务B: 调查社区反馈与使用案例 → researcher
    ├── 任务C: 撰写深度文章 → writer (依赖 A+B)
    ├── 任务D: 审核文章 → reviewer (依赖 C)
    └── 任务E: 发布到 GitHub → publisher (依赖 D)
```

#### ⚠️ 踩坑汇总（重点！）

这是整个案例中**坑最多**的阶段，老师演示时遇到了以下问题：

| # | 问题 | 原因 | 解决方法 |
|---|------|------|---------|
| 1 | **任务被自动阻塞** | Writer 写完后自己把自己标记为 blocked，等待审核 | 手动 `hermes kanban unblock <task_id>` |
| 2 | **Agent 自己阻塞自己** | Agent 说 "我要标记完成，但我自己没法标记完成" | 这是设计问题，需要手动干预 |
| 3 | **新记忆不生效** | 修改 SOUL.md 后 Agent 仍直接回答 | 微信中发 `/new` 重置会话 |
| 4 | **发布找不到审核输出** | Publisher 找不到 review 完成的文件 | 告诉它 "最终的文档在任务 xxx 的输出中" |
| 5 | **发布完成后仍阻塞** | Publisher 发布成功但状态没更新 | 加 comment 后 unblock |
| 6 | **GitHub 访问慢** | 国内访问 GitHub 不稳定 | 多等一会儿，或换邮箱发布 |

**具体操作**：

```bash
# 1. 查看任务状态
hermes kanban show <board_name>

# 2. 手动解除阻塞
hermes kanban unblock <task_id>

# 3. 给任务加备注
hermes kanban comment <task_id> "发布完成之后直接结束，不要做什么标记"

# 4. 重置微信会话
# 在微信中发送：/new
```

#### 💡 要点

- **第一次跑通需要人工介入 3-5 次**，这是正常的。老师原话："第一次运行它显得不是那么的聪明，这是很正常的，因为刚开始跑嘛。"
- **后续会越来越顺**：跑通一次后，用 Memory + Skill 把流程记下来，下次 Agent 就知道怎么走了
- **模型质量影响流畅度**：用 Claude 比 DeepSeek 更流畅，但 DeepSeek 也能跑通
- **不要期望一次完美**：老师演示时也反复调整了好几次

### 5.2 SEO 插件手动创建与部署

#### 🎯 思路

SEO 插件用 Python 代码实现文章元数据检查（标题长度、描述长度、关键词密度），比让大模型检查**更快、更便宜**。

#### 📋 步骤

**1. 创建插件目录和文件**

```bash
# 进入 Hermes 根目录
cd ~/.hermes

# 创建 plugins 目录（如果没有）
mkdir -p plugins/seo-checker
```

**2. 创建 plugin.yaml**

```bash
# 用 VS Code 创建文件
code plugins/seo-checker/plugin.yaml
```

内容：

```yaml
name: seo-checker
version: "1.0"
description: Checks blog post SEO metadata quality.
```

**3. 创建 `__init__.py`**

```bash
code plugins/seo-checker/__init__.py
```

内容见原笔记的 5.4 节（Python 代码，实现 `check_seo` 工具）。

**4. 启用插件**

```bash
hermes plugins enable seo-checker
```

**5. 部署到 reviewer profile**

```bash
# 方法一：复制插件目录
cp -r ~/.hermes/plugins ~/.hermes/profiles/reviewer/

# 方法二：在 reviewer 中启用
reviewer plugins enable seo-checker
```

#### ⚠️ 踩坑

- **plugins 目录可能不存在**：需要手动创建 `mkdir -p plugins/seo-checker`
- **路径不要搞错**：插件在 `~/.hermes/plugins/` 下，不是在 profile 目录下
- **启用后需要测试**：让 reviewer 写一篇文章然后审核，看是否会调用 `check_seo`

### 5.3 Hooks 与 No-Agent Cron

这两个原笔记已写清楚，实操要点：

**Hooks**：用于记录 Token 消耗，但老师认为**直接用 DeepSeek 官网或桌面客户端查看更方便**，不是必须的。

**No-Agent Cron**：纯脚本监控博客站点健康状态，不需要 LLM 参与。

```bash
# 创建监控脚本
cat > ~/.hermes/scripts/blog-health-check.sh << 'EOF'
#!/bin/bash
STATUS=$(curl -s -o /dev/null -w "%{http_code}" https://yourname.github.io/blog/)
if [ "$STATUS" != "200" ]; then
  echo "BLOG DOWN: HTTP $STATUS"
  exit 1
fi
echo "OK: Blog healthy, status=$STATUS"
EOF

# 创建定时任务
hermes cron create "every 30m" \
  --no-agent \
  --script blog-health-check.sh \
  --deliver wechat \
  --name "blog-health-check"
```
