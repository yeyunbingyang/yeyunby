# Karpathy 四大原则

> **一句话**：一个 `CLAUDE.md` 文件，四条原则，零安装成本，改变 AI Agent 的编程行为方式。

## 一、背景

**Andrej Karpathy**（前 Tesla AI 总监、前 OpenAI 联合创始人）在大量使用 LLM 编程后，总结了 AI Agent 最常见的三大坑点：

| 坑点 | 表现 |
|------|------|
| **错误假设** | 不展示权衡，直接按错误的理解开干 |
| **过度复杂** | 引入不必要的抽象、框架、依赖 |
| **正交修改** | 改 A 的时候顺手改了 B，引入意外 Bug |

他的解法极简——**一个 `CLAUDE.md` 文件，四条原则**。不需要安装任何 Skill 包，不需要学习斜杠命令，直接把原则写进项目根目录，Agent 每次启动自动加载。

**Stars**：156k（Skills 生态中最高，超过 anthropics/skills 的 141k）

## 二、四大原则详解

### 原则一：Think Before Coding（先思考再编码）

**解决的问题**：错误假设、隐藏困惑、不展示权衡

**核心要求**：
- 在写任何代码之前，先分析问题
- 列出可能的方案
- 指出每个方案的权衡
- 确认理解正确后再动手

**实际效果**：
```
❌ 没有原则时：
用户：帮我加一个导出 CSV 的功能
Agent：好的，马上写...（直接开干，可能选错方案）

✅ 有原则时：
用户：帮我加一个导出 CSV 的功能
Agent：先分析一下——
  需求：从当前数据列表导出 CSV
  方案 A：Python csv 模块（标准库，零依赖）
  方案 B：pandas（功能强但引入大依赖）
  方案 C：手动拼接字符串（简单但易出错）
  推荐：方案 A，因为这是标准库，无需额外安装
开始实现...
```

### 原则二：Simplicity First（优先简单方案）

**解决的问题**：过度复杂、臃肿抽象

**核心要求**：
- 优先选择最简单的方案
- 不要引入新的框架/库，除非绝对必要
- 不要为了"未来可能需要的扩展性"而增加复杂度
- 代码越少越好

**实际效果**：
```
❌ 没有原则时：
用户：加一个用户配置功能
Agent：引入 yaml 库、创建配置类、写配置验证器、加缓存...

✅ 有原则时：
用户：加一个用户配置功能
Agent：最简单的方案——
  用 JSON 文件存配置，Python 内置 json 模块就够了
  不需要引入第三方库
  配置就一个 dict，不需要包装成类
```

### 原则三：Surgical Changes（精准手术式修改）

**解决的问题**：正交修改、误伤无关代码

**核心要求**：
- 修改时只改需要改的地方
- 不要顺手重构无关代码
- 不要"顺便"修一下旁边的格式问题
- 一次只做一件事

**实际效果**：
```
❌ 没有原则时：
用户：修复登录页面的按钮颜色
Agent：改按钮颜色 → "顺便"重构了 CSS 结构 → 
      "顺便"改了布局 → "顺便"升级了依赖 →
      引入回归 Bug

✅ 有原则时：
用户：修复登录页面的按钮颜色
Agent：只改按钮颜色这一个属性。
  不改布局、不改其他按钮、不重构 CSS。
  改动范围：1 个文件，1 行代码。
```

### 原则四：Goal-Driven Execution（目标驱动执行）

**解决的问题**：测试先行、可验证成功标准

**核心要求**：
- 每步完成后验证是否达到目标
- 测试通过才算完成
- 不要"看起来对了"就交差
- 有明确的完成标准

**实际效果**：
```
❌ 没有原则时：
Agent：代码写完了，看起来没问题（实际没运行过）

✅ 有原则时：
Agent：代码写完了，运行测试验证——
  ✓ 测试 1：导出 CSV 格式正确
  ✓ 测试 2：中文不乱码
  ✓ 测试 3：空数据处理正常
  全部通过，确认完成。
```

## 三、使用方式

### 方式一：写入项目 CLAUDE.md（推荐）

在项目根目录创建 `CLAUDE.md`：

```markdown
# CLAUDE.md

## Think Before Coding
在写任何代码之前，先分析问题、列出可能的方案、指出每个方案的权衡。确认理解正确后再动手。

## Simplicity First
优先选择最简单的方案。不要引入新的框架或库，除非绝对必要。不要为"未来可能需要的扩展性"增加复杂度。

## Surgical Changes
修改时只改需要改的地方。不要顺手重构无关代码，不要"顺便"修旁边的格式问题。一次只做一件事。

## Goal-Driven Execution
每步完成后验证是否达到目标。测试通过才算完成。"看起来对了"不够，必须实际运行验证。
```

### 方式二：写入全局配置

对所有项目生效：

- **Claude Code**：`~/.claude/CLAUDE.md`
- **Codex**：`~/.codex/AGENTS.md`
- **Cursor**：项目级 `.cursorrules`

### 方式三：作为 Hermes 记忆注入

在 Hermes Agent 中，这些原则已经内置在我的行为准则中（见 AGENTS.md 和系统提示词）。你不需要额外配置。

## 四、与其他方案的叠加效果

四大原则是**基座**——可以叠加在任何 Skill 包之上：

```
karpathy 四大原则（基座）
    │
    ├─ + agent-skills → 有纪律的工程流程
    ├─ + Waza         → 有习惯的日常开发
    ├─ + mattpocock   → 有对齐的需求管理
    └─ + myclaude     → 有编排的多 Agent 协作
```

**为什么可以叠加**：
- 四大原则是**行为约束**（怎么做事）
- 其他 Skill 包是**工作流程**（做什么事）
- 两者正交，互不冲突

## 五、实际对话对比

### 没有四大原则

```
你：帮我优化一下这个函数

Agent：好的，我来重构它——
（直接开始改代码，可能引入新依赖、改了一堆无关代码、
 没测试就交差）
```

### 有四大原则

```
你：帮我优化一下这个函数

Agent：（Think）先分析这个函数在做什么——
  这是一个数据格式化函数，输入原始数据，输出格式化后的字符串。
  
（Simplify）最简单的优化方式——
  不需要引入新库，用 Python 标准库的字符串方法就够了。

（Surgical）只改这个函数本身——
  不改调用方、不改其他函数、不改测试。

（Goal-Driven）优化后运行测试验证——
  确保输入输出与原来一致，性能有提升。

开始吗？
```

## 六、什么时候用

| 场景 | 效果 |
|------|------|
| **新项目初始化** | 从一开始就让 Agent 养成好习惯 |
| **Agent 行为失控** | 经常过度设计、改无关代码时，四大原则是解药 |
| **叠加到任何 Skill 包** | 作为基座，不影响其他 Skill 的正常使用 |
| **团队统一 Agent 行为** | 一个文件，所有人共享相同的 Agent 纪律 |

## 七、注意事项

1. **不是银弹** — 四大原则约束行为，但不提供具体工作流。需要和其他 Skill 包配合使用
2. **可能增加对话轮次** — Think 阶段会多一轮确认，但长远看节省返工时间
3. **需要 Agent 支持 CLAUDE.md** — Claude Code / Codex 原生支持，其他工具需确认
4. **中文版 vs 英文版** — 上述内容是中文版。原版是英文，效果一致
