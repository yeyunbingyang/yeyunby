# 爬虫基础

## 一句话结论

> 爬虫的本质是模拟浏览器发送 HTTP 请求获取数据，核心技能是抓包分析——按"静态 HTML → JS/Ajax → CSS/字体/图片"三层递进定位目标数据所在的请求，然后模拟该请求即可拿到数据。

## 爬虫学科特点

### 知识点碎片化

爬虫方向的知识点非常碎片化。不同于 Web 开发（Django、Flask、Tornado 等框架虽然套路不同，但整体原理一致，换了框架只是换一种写法），爬虫面对的是各种各样不同类型的网站。每个网站虽然总体技术相似，但都有自己的特点：

- 有的需要登录
- 有的有验证码
- 有的涉及支付流程

这就导致写爬虫时，需要根据不同网站使用不同的手段和技术。工作中可能遇到从未见过的情况，需要针对性地学习专门的破解技术。

### 入门简单，后期更难

爬虫入门比 Web 开发简单——发一个 HTTP 请求就能拿到数据。但后期的难点在于：**爬虫工程师实际上是在与网站的开发和运维人员做对抗**。

这是一个不断博弈的过程：
1. 你写好爬虫，能正常拿到数据
2. 网站运维/开发添加了反爬措施，爬虫失效
3. 你需要研究新的方式再次获取数据
4. 网站反爬不断升级，你的爬虫也需要不断升级

有些网站被很多人爬过，反爬措施已经非常成熟，可能会出现爬不下来的情况。

### 以案例为导向

爬虫阶段不像 Web 阶段那样有一个完整的项目贯穿始终。因为每个网站都不一样，可能遇到各种情况，所以爬虫课程通常是以**某个具体网站的爬虫案例**来讲解一项技术，而不是围绕一个完整项目展开。

### 技能要求更杂

相比于 Web 开发——掌握框架、熟悉业务即可——爬虫要求掌握的东西更多更杂。有些东西甚至从未接触过或想象不到，例如：

- 爬取银行网站时，可能需要操作 U 盾这类硬件
- 可能涉及自动化操作、图像识别、JS 逆向等跨领域技术

### 法律灰色地带

Web 开发做网站是合法的（除非做不良网站）。而爬虫批量采集别人公开在互联网上的数据，虽然数据是公开的，但批量采集可能涉及法律问题。目前国内法律对爬虫的评判还没有非常明确的制度，爬虫实际上属于灰色地带。

## HTTP 协议复习

### HTTP 与 HTTPS 的区别

- **HTTP**：超文本传输协议，明文传输，端口 80
- **HTTPS**：HTTP + SSL/TLS，加密传输，端口 443，更安全

### 请求头（爬虫最关注的三项）

| 请求头        | 作用                   | 爬虫中的用途            |
| ---------- | -------------------- | ----------------- |
| User-Agent | 标识客户端类型（浏览器/操作系统/设备） | 伪装成正常浏览器，绕过基础反爬检测 |
| Referer    | 标识当前请求从哪个页面跳转过来      | 处理防盗链，应对来源校验      |
| Cookie     | 携带用户的身份和状态信息         | 维持登录态，绕过需要认证的页面   |

> 这三个是**最常用**但不是唯一的——实际爬虫中根据目标网站的需要关注对应的请求头。

### 响应头

- **Set-Cookie**：服务器要求客户端设置的 Cookie，用于状态跟踪和会话保持

### 状态码

- **爬虫中不可全信状态码**：一切以响应体的实际内容为准
- 服务器可能返回 200 但内容是错误页面或验证码页面
- 也可能返回 404 但实际上是反爬拦截
- 判断数据是否成功获取，看响应内容中是否包含目标数据，而不是看状态码

## 浏览器发请求的过程

浏览器打开一个页面时，实际上发出了**多次请求**：

1. 首先请求 HTML 文档（静态文件）
2. 解析 HTML 后发现引用了 CSS、JS、图片、字体等资源
3. 再次发送请求获取这些资源
4. 将所有资源**渲染**成用户最终看到的页面

所以用户在浏览器中看到的结果，是**多次请求的响应共同渲染的产物**。

## 爬虫发请求的过程

爬虫与浏览器有本质区别：

- 爬虫通常**只发送一次请求**，拿到响应后**不做渲染**
- 爬虫不会自动加载 CSS、JS、图片等外部资源
- 爬虫拿到的是原始的 HTML 响应文本，而不是渲染后的页面

这意味着：**浏览器中看到的数据，不一定在你模拟的那个请求的响应中**。数据可能是在另一个 Ajax 请求中异步加载的，也可能是 JS 动态生成的。

因此爬虫的核心工作就是——**抓包分析**，从浏览器的多次请求中找到真正包含目标数据的那个请求，然后用代码模拟它。

## 数据查找方法：骨骼 → 肌肉 → 皮肤

在浏览器开发者工具（DevTools → Network）中，所有请求按类型分类。为了高效找到数据所在位置，按以下三层顺序递进查找，**找到即停止，不再继续**。

### 第一层：骨骼 — 静态文件（Document）

这是 HTML 文档本身，浏览器收到的第一个响应。

**查找步骤**：
1. 打开 DevTools → Network 面板
2. 刷新页面，在类型筛选栏选择 **Doc**（Document）
3. 点击该请求，查看 **Response** 标签页
4. Ctrl+F 搜索目标关键词
5. 如果找到 → 数据就在静态 HTML 中，直接模拟这个请求的 URL 和 Headers 即可

**示例**：在百度搜索 "python"，打开 DevTools 抓包，在 Document 请求的 Response 中搜索 "python"，如果能找到 482 个匹配结果，说明数据就在静态页面中。

### 第二层：肌肉 — JS / Ajax（XHR）

如果 Document 中找不到目标数据，说明数据可能是动态加载的。

**查找步骤**：
1. 在 Network 面板中筛选 **XHR** 或 **JS** 类型
2. 逐个查看这些请求的 Response
3. 搜索目标关键词
4. 找到后 → 模拟该 Ajax 接口请求（注意请求方法、URL、Headers、参数）

很多现代网站的数据是通过 Ajax 异步请求后端接口获取的，前端拿到 JSON 数据后再用 JS 渲染到页面上。

### 第三层：皮肤 — CSS / 字体 / 图片

如果前两层都找不到，数据可能隐藏在样式或媒体资源中：

- **CSS 文件**：通过 ::before / ::after 伪元素的 content 属性插入文本
- **自定义字体**：将文字编码为自定义字体文件，页面显示正常但源代码是乱码（需要字体解析）
- **图片**：数据以图片形式展示（需要 OCR 识别）

这类情况相对少见，但处理起来更为复杂，需要专门的解析手段。

### 查找口诀

> 先骨骼 → 再肌肉 → 最后皮肤。逐层排查，找到即停，模拟该请求即可。

### 实战流程总结

`
打开 DevTools → Network → 刷新页面
  ↓
筛选 Document 类型 → 搜索关键词
  ├─ 找到 → 复制 URL + Headers → 模拟请求（结束）
  └─ 未找到 ↓
筛选 XHR / JS 类型 → 逐个搜索关键词
  ├─ 找到 → 复制接口 URL + Headers + 参数 → 模拟请求（结束）
  └─ 未找到 ↓
检查 CSS / 字体 / 图片 → 对应解析手段
`

## 课程总结

- HTTP 协议复习：重点掌握 User-Agent、Referer、Cookie 三个请求头在爬虫中的用途，以及 Set-Cookie 响应头
- 状态码在爬虫中**不可全信**，一切以响应体实际内容为准
- 浏览器渲染页面 = 多次请求响应共同作用的结果；爬虫只发一次请求，不做渲染
- 爬虫的核心工作流：**抓包分析 → 找出关键请求 → 模拟请求 → 获取数据**
- 数据查找按「骨骼（Document）→ 肌肉（JS/Ajax）→ 皮肤（CSS/字体/图片）」三层递进

## 关键概念

- **抓包**：通过浏览器 DevTools（Network 面板）分析页面加载过程中的所有网络请求，定位目标数据所在的请求
- **反爬**：网站为防止数据被批量采集而采取的技术措施（UA 检测、IP 封禁、验证码、JS 混淆、字体反爬等）
- **模拟请求**：用代码构造与浏览器一致的 HTTP 请求（URL、Headers、参数等），向服务器请求并拿到响应数据
- **静态数据**：直接存在于 HTML 源代码中的数据，Page Source 中可见
- **动态数据**：通过 Ajax 异步加载或 JS 动态生成的数据，需要抓包才能找到

## 可行动建议

- 接到爬虫任务 → 先打开 DevTools → Network → 勾选 Preserve log → 刷新页面 → 观察所有请求
- 在 Document 响应中搜索目标数据 → 找到则最简单，直接用 
equests.get() 模拟
- Document 中找不到 → 在 XHR/Fetch 请求中逐个搜索 → 找到后模拟该接口
- 前两者都找不到 → 检查是否是 JS 动态计算生成，或隐藏在 CSS/字体中
- 确定目标请求后 → 复制 cURL → 用代码模拟 → 先确认能拿到数据，再写解析逻辑
