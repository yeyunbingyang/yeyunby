## 1. 什么是 Prompt Engineering

Prompt Engineering（提示词工程）不是"写几句漂亮话哄 AI 开心"，而是一门**结构化沟通的技术**——它研究的是：如何通过精确控制输入（Prompt），来最大化地引导大语言模型（LLM）输出符合预期的结果。

### 1.1 为什么需要它？

大语言模型本质上是**概率机器**。它并不"理解"你的意图，只是在根据训练数据预测"下一个最可能出现的词"。

因此：

- 模糊的需求 → 模糊的回答
    
- 清晰的约束 → 清晰的输出
    
- 错误的假设 → 幻觉（Hallucination）
    

### 1.2 两个核心认知

表格

|认知|含义|实践启示|
|:--|:--|:--|
|**AI 是实习生，不是神**|它知识广博但缺乏常识判断，需要明确指令|不要假设它"应该懂"|
|**Prompt 是程序接口**|每一个词都是参数，影响输出分布|像写代码一样严谨对待每一个字|

## 2. 核心原则：与 AI 沟通的心法

在掌握任何框架之前，先内化这 5 条心法：

### 原则一：先定义问题，再定义答案

> 错误的开始："帮我写一篇关于人工智能的文章。"  
> 正确的开始："我需要向非技术背景的投资者解释 AI 的商业价值，重点讲降本增效。"

**问题比答案更重要。** 80% 的糟糕输出源于提问者自己都没想清楚要什么。

### 原则二：Context 决定一切

AI 没有"上下文记忆"（除了当前对话窗口）。你给它的背景信息越完整，它越能站在你的立场思考。

### 原则三：具体优于抽象

- ❌ "写得专业一点"
    
- ✅ "使用行业术语，引用具体数据，避免口语化表达"
    

### 原则四：约束即创造力

限制不是束缚，而是**聚焦**。告诉 AI "不要做什么"往往比"做什么"更能提升质量。

### 原则五：迭代优于一次性完美

没有人第一次写 Prompt 就能得到完美结果。**测试 → 观察 → 调整** 是常态。

## 3. 基础框架：六步问诊法详解

基于"医生问诊"的类比，我们将其升级为可复用的 **PE-R-COST 框架**（Persona-Expectation-Restriction-Context-Objective-Style-Template）。

### 3.1 框架总览


```plain
┌─────────────────────────────────────────┐
│  Step 1: Persona（角色）                │
│  → 你是谁？（专家身份）                 │
├─────────────────────────────────────────┤
│  Step 2: Context（背景）                │
│  → 你的现状、目标、限制条件             │
├─────────────────────────────────────────┤
│  Step 3: Objective（任务）              │
│  → 具体要做什么？                       │
├─────────────────────────────────────────┤
│  Step 4: Restriction（约束）            │
│  → 不要做什么？边界在哪里？             │
├─────────────────────────────────────────┤
│  Step 5: Style（风格）                  │
│  → 用什么语气、格式、结构？             │
├─────────────────────────────────────────┤
│  Step 6: Template（参考）               │
│  → 给示例，让 AI 模仿                   │
└─────────────────────────────────────────┘
```

### 3.2 逐层拆解

#### Step 1: Persona（角色设定）

**原理**：通过角色扮演激活模型在特定领域的知识分布。

**技巧**：

- 选择**特征鲜明、公众认知度高**的角色（如张雪峰、巴菲特、鲁迅）
    
- 补充**专业资质**（"10 年经验的..."、"发表过 50 篇论文的..."）
    
- 可以叠加多个角色（"你既是程序员又是产品经理"）
    

**示例**：

```plain
❌ 你是一个专家。
✅ 你是一位拥有 15 年临床经验的消化内科主任医师，
   擅长用通俗易懂的语言向患者解释复杂病情。
```

#### Step 2: Context（背景信息）

**只需三个维度**：

| 维度     | 问题        | 示例                       |
| :----- | :-------- | :----------------------- |
| **现状** | 你现在是什么情况？ | "我是一名大二计算机专业学生"          |
| **目标** | 你想达成什么？   | "想在大三暑假拿到大厂实习 offer"     |
| **限制** | 你有什么约束？   | "每天只有 2 小时学习时间，预算 500 元" |

**黄金法则**：提供**必要且充分**的信息。过多无关信息会稀释重点，过少则导致输出偏离。

#### Step 3: Objective（明确任务）

使用**动词开头**的祈使句：

- 分析、对比、总结、列出、生成、翻译、改写、评估...
    

**进阶技巧**：将大任务拆解为子任务


```plain
请分三步完成：
1. 先分析原文的核心论点
2. 再找出其中的逻辑漏洞
3. 最后给出改进建议
```

#### Step 4: Restriction（约束条件）

约束分两类：

**内容约束**：

- "不要提及竞品名称"
    
- "只使用 2023 年以后的数据"
    
- "避免使用专业术语，用大白话解释"
    

**形式约束**：

- "字数控制在 300 字以内"
    
- "用 Markdown 表格呈现"
    
- "分三点论述，每点不超过 50 字"
    

#### Step 5: Style（风格与格式）

**语气控制词汇表**：

| 场景   | 关键词                  |
| :--- | :------------------- |
| 商务正式 | "正式、严谨、客观、数据驱动"      |
| 社交媒体 | "轻松、幽默、有网感、多用 emoji" |
| 学术写作 | "客观、引用规范、逻辑严密、批判性分析" |
| 教育辅导 | "耐心、鼓励、循序渐进、举例说明"    |
| 创意写作 | "富有想象力、诗意、画面感强、打破常规" |

**格式控制**：

- 列表、表格、JSON、XML、Markdown、代码块
    
- 分段标题层级（H1/H2/H3）
    
- 重点加粗、高亮
    

#### Step 6: Template（参考示例）

**One-shot / Few-shot 技巧**：

直接给 AI 一个"标准答案"样本，让它模仿：


```plain
请参考以下格式回复：

【问题诊断】...
【解决方案】...
【执行步骤】...
【风险提示】...
```

或者给多个示例让它学习规律（Few-shot Learning）：

```plain
示例 1：
输入："今天天气很好"
输出：{"sentiment": "positive", "confidence": 0.95}

示例 2：
输入："这部电影太烂了"
输出：{"sentiment": "negative", "confidence": 0.92}

现在请处理：
输入："虽然剧情一般，但特效很震撼"
输出：
```

### 3.3 完整示例：六步法实战

**场景**：给领导写一份项目延期汇报

```
【Persona】
你是一位拥有 10 年经验的互联网大厂项目经理，擅长在不利情况下进行高情商沟通。

【Context】
- 现状：我们负责的 APP 重构项目原定 6 月 30 日上线，但因第三方接口延迟，预计要延期 2 周
- 目标：向 CTO 汇报情况，争取理解和支持，同时展示我们的补救措施
- 限制：不能推卸责任给第三方，要体现团队的主动性和专业性

【Objective】
请帮我起草一份邮件，向 CTO 汇报项目延期情况。

【Restriction】
- 邮件正文不超过 300 字
- 先讲补救措施，再讲延期原因（先给方案，再给问题）
- 不要出现"不可抗力"等推卸责任的词汇
- 结尾要给出明确的新时间节点

【Style】
- 语气：尊敬、自信、有担当
- 格式：标准商务邮件格式（称呼-正文-结尾-署名）
- 语言：简洁有力，一句一段，避免长句

【Template】
参考以下口吻（但不要照搬）：
"针对当前情况，团队已启动 B 方案...预计可在 X 月 X 日完成交付..."
```

## 4. 进阶技术：从"会说话"到"会操控"

### 4.1 Chain-of-Thought（思维链，CoT）

**原理**：让 AI "大声思考"，把推理过程展示出来，能显著提升复杂任务的准确率。

**触发方式**：

```plain
"请一步一步思考。"
"Let's think step by step."
"请展示你的完整推理过程。"
```

**示例**：

```plain
问题：一个农场有鸡和兔，头共 35 个，脚共 94 只。鸡兔各几只？

普通 Prompt：直接给答案 → 可能算错
CoT Prompt："请一步一步列出方程并求解。"
→ 输出：设鸡 x 只，兔 y 只... x + y = 35... 2x + 4y = 94... 解得...
```

**进阶：Zero-shot CoT**

```plain
在回答之前，请先深呼吸，然后逐步分析。
```

### 4.2 ReAct 模式（Reasoning + Acting）

**原理**：让 AI 在"思考"和"行动"之间交替，适合需要工具调用或外部信息检索的任务。

**结构**：

```plain
Thought: 我需要先搜索最新数据...
Action: 搜索"2024 年中国 GDP 增速"
Observation: 搜索结果显示...
Thought: 基于这些数据，我可以得出结论...
```

### 4.3 Self-Consistency（自一致性）

**原理**：对同一个问题生成多条推理路径，投票选出最一致的答案。

**Prompt 写法**：

```plain
请用三种不同的方法解答这个问题，然后比较结果，
选择最可靠的答案并说明理由。
```

### 4.4 Tree of Thoughts（思维树，ToT）

**原理**：让 AI 探索多条思考路径，像下棋一样评估每一步的价值。

**适用场景**：创意写作、策略规划、复杂决策

**Prompt 写法**：

```plain
针对这个问题，请生成 3 个不同的解决思路。
对每个思路，评估其优缺点和实施难度。
最后推荐最佳方案并说明理由。
```

### 4.5 结构化输出（JSON/XML 模式）

**适用场景**：程序对接、数据分析、批量处理

**Prompt 写法**：

```plain
请将以下信息提取为 JSON 格式，字段包括：
- name（姓名）
- age（年龄，整数）
- skills（技能数组）
- summary（一句话总结）

要求：
1. 只输出 JSON，不要任何解释文字
2. 如果信息缺失，字段值设为 null
3. 确保 JSON 格式合法
```

### 4.6 角色叠加与对抗（Red Teaming）

**原理**：让 AI 同时扮演多个角色进行辩论，以获得更全面的视角。

**Prompt 写法**：

```plain
请你分别扮演以下三个角色，就"是否该全面远程办公"进行辩论：
1. 人力资源总监（关注员工福祉和招聘）
2. 财务总监（关注成本和效率）
3. 技术总监（关注协作和信息安全）

每个角色先陈述立场，然后互相反驳，最后达成妥协方案。
```

## 5. 常见误区与避坑指南

### 误区 1：Prompt 越长越好

**真相**：冗余信息会稀释重点，增加模型"走神"的概率。

**对策**：

- 使用"请只关注以下信息..."
    
- 将背景信息放在最后（模型对首尾信息记忆更强）
    
- 删除一切形容词和副词，保留事实和指令
    

### 误区 2：角色设定万能

**真相**：角色设定对创意类、咨询类任务有效，但对数学、编程等逻辑任务作用有限。

**对策**：

- 逻辑任务 → 用 CoT、明确步骤
    
- 创意任务 → 用 Persona、风格词
    
- 信息提取 → 用结构化输出、Few-shot
    

### 误区 3：一次性追求完美

**真相**：Prompt Engineering 是迭代过程，不是一锤子买卖。

**对策**：使用**TIRE 迭代法**：

```plain
Test（测试）→ Inspect（检查输出）→ Refine（调整 Prompt）→ Evaluate（评估）
```

### 误区 4：忽视模型的"幻觉"

**真相**：AI 会自信地编造事实、数据、引用。

**对策**：

- 明确要求"如果不确定，请说明"
    
- 对事实性任务要求提供来源
    
- 对关键数据要求"只使用我提供的信息，不要编造"
    

### 误区 5：混淆"指令"和"内容"

**真相**：如果把指令和待处理内容混在一起，模型可能把指令也当作内容处理。

**对策**：使用分隔符明确区分：

```plain
请总结以下文章的核心观点：

"""
[这里是文章内容]
"""

要求：
1. ...
2. ...
```

## 6. 领域实战模板库

### 6.1 编程开发
**代码生成**：
```
你是一位资深 Python 后端工程师，擅长 Django 和 FastAPI。

任务：请帮我写一个用户注册的 API 接口。

要求：
- 使用 FastAPI 框架
- 包含输入校验（邮箱格式、密码强度）
- 使用 SQLAlchemy 操作数据库
- 包含异常处理和日志记录
- 添加中文注释说明每个函数的作用
- 输出完整可运行的代码，不要省略任何部分
```
**代码 Review**：
```
请作为代码审查专家，对以下代码进行审查：

"""
[代码]
"""

请按以下维度给出反馈：
1. 【潜在 Bug】是否有逻辑错误或边界情况未处理？
2. 【性能】是否有性能瓶颈或可优化点？
3. 【安全】是否有 SQL 注入、XSS 等安全隐患？
4. 【可读性】命名、注释、结构是否清晰？
5. 【最佳实践】是否符合 Pythonic 风格或团队规范？

每个问题请给出：问题描述 + 具体位置 + 改进建议代码片段
```
### 6.2 数据分析

**数据解读**：

```markdown
你是一位数据分析师，擅长从业务角度解读数据。

背景：我们是一家电商公司，以下是我们 Q3 的销售数据...

任务：
1. 找出 3 个最重要的数据洞察
2. 每个洞察需包含：现象描述、可能原因、业务建议
3. 用非技术语言撰写，适合向 CEO 汇报
4. 输出格式：Markdown 表格 + 简短总结
```

### 6.3 内容创作

**小红书文案**：

```
你是一位拥有 50 万粉丝的生活方式博主，擅长写爆款小红书笔记。

任务：为一款便携式咖啡机写推广文案。

要求：
- 标题要吸睛，使用 emoji
- 正文分 3-5 段，每段不超过 3 行
- 包含 3 个使用场景（办公室、户外、旅行）
- 结尾引导互动（提问或征集评论）
- 添加 5 个相关 hashtag
- 语气：真实分享感，不要像广告
```

### 6.4 学习与教育

**费曼学习法助手**：

```
你是一位耐心的大学助教，精通费曼学习法。

任务：请用费曼学习法帮我理解"区块链技术"。

要求：
1. 先用类比（如：账本、快递追踪）解释核心概念
2. 然后逐步深入技术细节
3. 每讲一个概念后，出一个简单的自测题
4. 如果我发现理解困难，请自动降级到更简单的类比
5. 语气：鼓励、耐心、像朋友在聊天
```

### 6.5 商业决策

**SWOT 分析**：

```markdown
你是一位战略咨询顾问，曾为多家 Fortune 500 公司服务。

背景：我们是一家成立 3 年的 SaaS 公司，主打 HR 管理系统，
      目前客户 200+，ARR 500 万，团队 30 人。
      计划明年进入东南亚市场。

任务：请做一份进入东南亚市场的 SWOT 分析。

要求：
- 每个维度至少 4 点
- 每点需有具体论据，不要泛泛而谈
- 最后给出优先级排序的行动建议
- 格式：Markdown 表格 + 行动计划清单
```

## 7. 评估与迭代：让 Prompt 越用越好

### 7.1 评估维度

|维度|问题|权重|
|:--|:--|:-:|
|**准确性**|内容是否正确？有无幻觉？|★★★★★|
|**完整性**|是否覆盖了所有要求？|★★★★☆|
|**相关性**|是否回答了真正的问题？|★★★★☆|
|**可读性**|格式是否清晰？语言是否流畅？|★★★☆☆|
|**合规性**|是否符合约束条件？|★★★★☆|

### 7.2 迭代检查清单

当你对输出不满意时，按此清单排查：

- [ ] **角色是否够具体？** "专家"→"10 年经验的某领域专家"
    
- [ ] **背景是否完整？** 是否漏了关键约束或目标？
    
- [ ] **任务是否单一？** 一个 Prompt 是否塞了太多任务？
    
- [ ] **格式是否明确？** 是否指定了输出结构？
    
- [ ] **示例是否给出？** Few-shot 能大幅提升一致性
    
- [ ] **是否要求逐步思考？** 复杂任务加 CoT
    
- [ ] **是否设定了边界？** "不要做什么"说清楚了么？
    
- [ ] **是否测试了温度参数？** 创意任务调高，事实任务调低
    

### 7.3 Prompt 版本管理建议

像管理代码一样管理你的 Prompt：

```plain
prompt_v1.md  # 初版
prompt_v2.md  # 增加了 Few-shot 示例
prompt_v3.md  # 优化了约束条件，减少了幻觉
prompt_final.md  # 生产环境使用
```

记录每次修改的原因和效果，形成自己的 Prompt 知识库。

## 结语

Prompt Engineering 的终极目标不是"学会写提示词"，而是**学会与 AI 协作**——知道什么时候该给详细指令，什么时候该放手让 AI 发挥；知道如何快速诊断问题出在 Prompt 还是模型能力；知道如何把一次性的技巧沉淀为可复用的工作流。

记住：**最好的 Prompt 工程师，不是最会"操控" AI 的人，而是最清楚自己需要什么的人。**
