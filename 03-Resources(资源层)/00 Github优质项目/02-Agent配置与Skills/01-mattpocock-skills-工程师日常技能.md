# mattpocock/skills 面向真实工程的软件开发技能包

> [!abstract] 一句话定位
> 一套强调“真实软件工程，而非 vibe coding”的 Agent Skills，通过小型、可修改、可组合的技能，把成熟工程实践嵌入 Claude Code、Codex 等编码 Agent 的工作流。

## 基本信息

| 项目 | 内容 |
|---|---|
| 仓库 | [mattpocock/skills](https://github.com/mattpocock/skills) |
| 作者 | Matt Pocock |
| 许可证 | MIT |
| 项目热度 | 约 191k Stars、16.4k Forks（2026-07-28） |
| 适用平台 | 支持 Agent Skills 标准的工具，包括 Codex；另提供 Claude Code 插件 |
| 核心理念 | 小型、可组合、可定制、模型无关，由开发者掌控流程 |

## 解决的问题

该项目没有试图接管完整研发流程，而是针对编码 Agent 的四类常见失败逐一提供技能：

| 常见失败               | 应对方式                           | 代表技能                                              |
| ------------------ | ------------------------------ | ------------------------------------------------- |
| Agent 没有理解真实需求     | 开工前持续追问并消除决策分支中的歧义             | `grill-me`、`grill-with-docs`                      |
| Agent 不理解项目术语、表达冗长 | 建立共享领域语言，维护 `CONTEXT.md` 和 ADR | `domain-modeling`、`grill-with-docs`               |
| 代码不能正常工作           | 强制短反馈循环、测试先行和系统诊断              | `tdd`、`diagnosing-bugs`                           |
| 代码库逐渐变成“大泥球”       | 设计深模块、持续识别架构改进机会               | `codebase-design`、`improve-codebase-architecture` |

## 技能组织方式

技能按“谁负责触发”划分，而不是按文件或研发阶段划分：

- **用户触发技能：** 由开发者显式调用，负责选择和编排工作流。
- **模型触发技能：** 可以由 Agent 根据任务自动调用，承载可复用的工程纪律。
- 用户触发技能可以调用模型触发技能，但不会再调用另一个用户触发技能。

### Engineering：用户触发

| 技能                              | 用途                                   |
| ------------------------------- | ------------------------------------ |
| `ask-matt`                      | 根据当前问题推荐适合的技能或工作流                    |
| `grill-with-docs`               | 深入澄清需求，同时更新领域模型、`CONTEXT.md` 和 ADR   |
| `triage`                        | 使用状态机和角色对 Issue 进行分类与推进              |
| `improve-codebase-architecture` | 扫描架构改进机会，以可视化报告辅助选择改进目标              |
| `setup-matt-pocock-skills`      | 为仓库配置 Issue Tracker、标签与文档位置          |
| `to-spec`                       | 将当前对话整理成规格并发布到 Issue Tracker         |
| `to-tickets`                    | 将计划或规格拆成带阻塞关系的 tracer-bullet tickets |
| `implement`                     | 按规格实施，在约定边界执行 TDD，并以代码审查收尾           |
| `wayfinder`                     | 将超过单次会话容量的大型工作拆成可逐步调查的路线图            |

### Engineering：模型触发

| 技能 | 用途 |
|---|---|
| `prototype` | 构建可丢弃原型，验证状态、逻辑或 UI 设计问题 |
| `diagnosing-bugs` | 按“复现→最小化→假设→插桩→修复→回归测试”诊断问题 |
| `research` | 基于高可信一手资料调研，并把带引用的结果写入仓库 |
| `tdd` | 以红—绿—重构循环逐个垂直切片实现功能或修复缺陷 |
| `domain-modeling` | 持续校准术语、边界场景、`CONTEXT.md` 与 ADR |
| `codebase-design` | 以深模块、小接口和清晰边界指导代码设计 |
| `code-review` | 分别从工程规范和规格一致性两个维度审查改动 |
| `resolving-merge-conflicts` | 按双方改动意图逐块处理 merge/rebase 冲突 |

### Productivity

| 类型 | 技能 | 用途 |
|---|---|---|
| 用户触发 | `grill-me` | 对计划或设计持续追问，直到关键决策闭合 |
| 用户触发 | `handoff` | 将当前对话压缩为可交接给其他 Agent 的文档 |
| 用户触发 | `teach` | 在有状态工作目录中开展跨会话教学 |
| 用户触发 | `writing-great-skills` | 编写和改进可靠 Agent Skills 的参考规范 |
| 模型触发 | `grilling` | 为 `grill-me` 和 `grill-with-docs` 提供通用追问循环 |

## 安装与初始化

### skills.sh：可修改副本

适合 Codex 或希望直接修改技能内容的用户：

```bash
npx skills@latest add mattpocock/skills
```

安装时选择需要的技能，并确保包含 `setup-matt-pocock-skills`。随后在目标仓库运行：

```text
/setup-matt-pocock-skills
```

初始化过程会询问：

- 使用 GitHub、Linear 还是本地文件作为 Issue Tracker。
- `triage` 应使用哪些工单标签。
- 规格、领域模型和 ADR 等文档保存在哪里。

### Claude Code 插件：托管更新

```text
/plugin marketplace add mattpocock/skills
/plugin install mattpocock-skills@mattpocock
```

- skills.sh 会复制可编辑的技能文件，适合按团队需求定制。
- Claude Code 插件以只读托管包交付，适合希望自动跟随上游更新的用户。
- 官方 README 表示原生 Codex 插件仍在规划中；Codex 当前可使用 skills.sh 方式安装。

## 推荐工作流

```text
setup-matt-pocock-skills
        ↓
grill-with-docs / grill-me
        ↓
to-spec → to-tickets
        ↓
implement → tdd
        ↓
code-review
```

大型或高不确定性任务可先使用 `wayfinder`；复杂缺陷改用 `diagnosing-bugs`；架构债务则独立运行 `improve-codebase-architecture`。

### 案例：为电商系统增加优惠券功能

假设现有电商系统已经支持购物车和下单，现在需要增加“用户在结算时使用优惠券”的功能。最初的需求只有一句话：

> 用户输入优惠码后，可以在订单中抵扣金额。

这句话无法直接指导开发，因为优惠券类型、适用范围、叠加规则、并发使用和退款处理都没有定义。下面用完整工作流把它逐步变成可验证的实现。

#### 第 1 步：初始化项目约定

首次在仓库中使用这套技能时运行：

```text
/setup-matt-pocock-skills
```

假设本项目选择：

- GitHub Issues 作为 Issue Tracker。
- `needs-triage`、`ready`、`in-progress`、`blocked` 作为工单标签。
- `docs/domain/` 保存领域模型，`docs/adr/` 保存架构决策。

**阶段产物：** Agent 知道去哪里创建规格和工单，也知道后续如何标记任务状态。此步骤通常每个仓库只执行一次。

#### 第 2 步：澄清需求并建立共享语言

由于这是代码功能，并且需要沉淀领域规则，使用：

```text
/grill-with-docs

我们要为结算流程增加优惠券功能。用户输入优惠码后，
系统校验优惠券并计算折扣，成功下单后核销。
```

Agent 不会立即写代码，而是围绕未决问题继续追问，例如：

1. 优惠券是固定金额、百分比，还是两者都支持？
2. 是否有最低消费、适用商品、有效期和用户范围限制？
3. 一张订单能否使用多张优惠券？是否能与促销活动叠加？
4. 优惠券是在创建订单时核销，还是支付成功后核销？
5. 支付失败、订单取消或退款时是否返还优惠券？
6. 同一张券被两个并发请求使用时，如何保证只核销一次？

经过确认，得到第一版业务规则：

- 支持固定金额券和百分比券。
- 每张订单最多使用一张券，不与其他订单级促销叠加。
- 折扣不能超过符合条件商品的金额。
- 创建订单时先锁定优惠券，支付成功后核销；订单超时或取消时释放。
- 同一张用户券只能成功锁定一次。

同时更新 `docs/domain/CONTEXT.md`，统一以下术语：

| 术语 | 含义 |
|---|---|
| 优惠券模板（Coupon） | 定义折扣方式、门槛、适用范围和有效期的规则 |
| 用户券（Coupon Grant） | 发放给特定用户的一次性优惠券实例 |
| 锁定（Reserve） | 下单期间临时占用用户券，防止并发重复使用 |
| 核销（Redeem） | 支付成功后将用户券永久标记为已使用 |
| 释放（Release） | 订单取消或超时后解除占用 |

**阶段产物：** 决策闭合的需求、统一术语和必要的 ADR。后续 Agent 不再混用“优惠码”“券规则”“用户券”等概念。

> [!tip]
> 如果只是讨论非代码方案，例如设计一场优惠券营销活动，可使用 `/grill-me`；涉及代码库和长期领域知识时优先使用 `/grill-with-docs`。

#### 第 3 步：生成可验收的规格

需求澄清后运行：

```text
/to-spec
```

生成的规格应包含范围、非目标、模块边界和验收标准。例如：

```text
目标：
- 结算接口支持提交 couponCode。
- 返回商品原价、优惠金额和应付金额。
- 创建订单时原子锁定用户券。

非目标：
- 本期不支持多券叠加。
- 本期不开发运营后台和发券功能。

验收标准：
- 无效、过期、不属于当前用户的券均返回明确错误。
- 优惠金额不能超过符合条件商品金额。
- 两个并发请求使用同一张用户券时只能有一个成功。
- 订单取消后用户券恢复为可用状态。
```

**阶段产物：** 一条包含明确边界和验收标准的规格 Issue，成为后续实现与审查的共同依据。

#### 第 4 步：拆成纵向可交付工单

运行：

```text
/to-tickets
```

不要简单地按“数据库、后端、前端”横向拆分，而是拆成可以独立验证的纵向切片：

| 工单 | 交付内容 | 依赖 |
|---|---|---|
| T1：校验优惠券 | 根据用户、商品、时间和门槛返回折扣结果 | 无 |
| T2：结算预览 | 结算接口接收优惠码并返回价格明细 | T1 |
| T3：锁定与释放 | 创建订单时锁券，取消或超时时释放 | T1 |
| T4：支付后核销 | 支付成功后核销，重复回调保持幂等 | T3 |
| T5：结算页交互 | 输入优惠码、显示折扣和错误信息 | T2 |

**阶段产物：** 一组具有阻塞关系、可单独验收的工单。T1 完成后即可验证核心规则，无需等待整个优惠券功能全部结束。

#### 第 5 步：按工单实施，并在边界处执行 TDD

选择已经满足依赖的 T1，然后运行：

```text
/implement
```

`implement` 会读取规格与工单，并在预先约定的业务边界调用 `tdd`。以“计算固定金额折扣”为例：

```text
红：先写测试——订单符合满 100 减 20 时，120 元应付 100 元。
绿：实现最少代码，使该测试通过。
重构：提取 DiscountPolicy，但不增加尚未要求的扩展机制。
```

随后逐个增加失败测试：

```text
- 订单金额 80 元，不满足 100 元门槛，应拒绝使用。
- 订单金额 10 元、优惠 20 元，应付金额最低为 0 元。
- 已过期的用户券应返回 COUPON_EXPIRED。
- 同一用户券并发锁定时只能有一个请求成功。
```

每完成一个纵向切片，都运行项目已有的类型检查、单元测试和集成测试，再进入下一张工单。

**阶段产物：** 与验收标准一一对应的测试、最小实现及实际验证记录，而不是一次生成整套未经运行的代码。

#### 第 6 步：按规范和规格双轴审查

全部工单完成后运行：

```text
/code-review
```

审查分成两个相互独立的维度：

1. **Standards 审查：** 检查重复逻辑、过深条件分支、命名不一致、事务边界模糊以及项目规范违反项。
2. **Spec 审查：** 对照原始规格，确认并发锁定、取消释放、金额封顶和错误码等验收标准是否全部实现。

例如，Standards 审查可能发现“优惠金额计算同时散落在结算预览和订单创建模块”；Spec 审查可能发现“订单超时释放已实现，但用户主动取消的释放路径遗漏”。两类问题分别修复并重新运行测试后，功能才算完成。

**最终产物：**

- 一份消除关键歧义的业务规格。
- 更新后的领域词汇表与架构决策。
- 一组带依赖关系、可独立验收的工单。
- 覆盖主要规则和并发边界的自动化测试。
- 通过工程规范与规格一致性审查的实现。

> [!success] 工作流的核心价值
> 这套流程并不是把一句需求直接扩写成大量代码，而是逐步缩小不确定性：先对齐“做什么”，再定义“怎样算完成”，然后以短反馈循环实现，最后分别检查“代码质量”和“需求完成度”。

## 适用场景

- 希望 Agent 遵循成熟工程实践，但不想采用接管全部流程的重型方法论。
- 需要在编码前充分澄清需求并沉淀统一领域语言。
- 希望通过规格、工单、TDD 和代码审查形成可验证的开发闭环。
- 团队需要一套可复制后再按项目修改的 Agent 工作流基线。
- TypeScript 项目以及其他对类型、测试和模块设计要求较高的代码库。

## 评估

### 优势

- 每个技能职责集中，可单独采用，不必一次引入整套流程。
- 强调需求对齐、反馈循环和代码设计，覆盖 Agent 编码最常见的失控点。
- 同时支持显式编排与模型自动触发，减少每次手工提示的负担。
- MIT 许可且技能文件可读，便于审查和团队定制。

### 注意事项

- `grill-*` 类技能倾向于充分追问，小任务中可能增加前置沟通成本。
- `triage`、`to-spec`、`to-tickets` 等技能依赖初始化时约定的 Issue Tracker 和文档结构。
- Claude Code 插件和 skills.sh 的更新模型不同：前者自动跟随上游，后者需要自行同步定制副本。
- 技能只能强化工作方法，仍需项目自身提供可运行的测试、类型检查和验证环境。
