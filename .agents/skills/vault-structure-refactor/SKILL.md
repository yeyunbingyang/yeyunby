# Obsidian 知识库结构重构

把目录重构视为信息架构迁移，而不是批量移动文件。先识别内容的职责和边界，再设计结构、生成映射、执行迁移并验证引用。

## 模式选择

根据用户意图选择最小充分模式：

- **审查**：只读取和分析，输出问题、目标目录树与迁移建议，不修改内容。
- **整理**：保持主要架构不变，处理归类、命名、多版本、重复附件和 MOC。
- **重构**：重新设计目录树，迁移文件，修复链接并更新导航。

用户只说“看看目录”时使用审查模式；明确说“整理、实施、重构、执行”时进入整理或重构模式。大规模移动前先给出目标树和迁移映射；用户已明确授权实施时，不重复询问可从本地规则确定的事项。

## 规则优先级

按以下顺序解释冲突：

1. 用户当前指令。
2. 仓库 `AGENTS.md`。
3. 仓库的命名、Frontmatter、归档与 MOC 规则。
4. 本技能。
5. 通用 Obsidian 习惯。

不要套用其他知识库技能中写死的 vault 路径或英文命名规则。

## 工作流程

### 一、建立基线

1. 定位知识库根目录和目标范围。
2. 阅读 `AGENTS.md`、顶级 MOC、Frontmatter 规范及命名规则。
3. 运行 `scripts/inspect-vault-structure.ps1`，统计目录、扩展名、Markdown、附件、空目录、重复哈希、疑似多版本文档和版本化实验资产。版本化资产只作为审查线索，不能按文件名直接判定冗余。
4. 检查工作区状态，区分用户已有修改与本次修改，不覆盖无关变更。
5. 记录迁移前文件数、体积、断链数和重复数，作为验收基线。

### 二、进行领域建模

先判断每个内容单元属于哪一种，不用单一目录规则处理所有文件：

| 类型 | 主要组织方式 | 判断依据 |
|---|---|---|
| 知识 | 领域 → 子主题 → 笔记 | 内容能长期复用，目录表达稳定主题 |
| 项目 | 项目 → 规范/记录/产出/数据 | 有目标、过程、版本、运行数据和交付物 |
| 资源 | 来源或资产类型 → 条目 | 主要保存外部材料、工具或素材 |
| 附件 | 跟随所属笔记或项目 | 不单独构成知识入口 |
| 归档 | 状态优先，目录辅助 | 已被替代但仍有审计或经验价值 |

识别主题重叠、粒度不一致、项目伪装成知识主题、附件侵入导航层和历史版本平行维护等问题。

### 三、设计目标结构

遵循以下原则：

- 一个文件只有一个物理归属，跨主题入口使用 Wikilink 或 MOC。
- 目录表达稳定边界；状态、平台、成熟度等易变维度放入 Frontmatter、标签或 Bases。
- MOC 只做链接、摘要和动态聚合，不承载长篇正文。
- 主题链接超过仓库阈值时拆分子 MOC；仓库没有阈值时，以 10 条作为审查点。
- 避免只有一个文件的无意义目录，也避免一个目录长期堆放几十个不同职责文件。
- 项目内部可使用 `00-入口`、`10-规范`、`20-工作记录`、`30-产出`、`90-维护数据`、`99-历史归档`，但只创建确有内容的层级。
- 附件命名和目录应能反推出所属项目或笔记。

输出目标目录树，并为每个新增、合并、改名或取消的目录写一句理由。

### 四、生成迁移映射

在移动前建立表格：

| 旧路径 | 新路径 | 动作 | 理由 | 引用影响 | 风险 |
|---|---|---|---|---|---|

动作只使用：保留、移动、改名、合并、归档、删除。删除必须有明确授权，并先确认内容已合并、文件为完全重复，或没有保留价值。

处理多版本时：

1. 确定权威文档。
2. 比较版本差异。
3. 把仍有效的经验合并进权威文档。
4. 有审计意义的旧版设为归档；无独立价值且用户授权时删除。
5. 修复所有对旧文件名和附件的引用。

### 五、执行迁移

按小批次执行，每批只处理一个主题或项目：

1. 创建目标目录和 MOC。
2. 合并文本，再移动或改名。
3. 更新 Frontmatter、Wikilink、嵌入路径和 Dataview `FROM`。
4. 更新相关子 MOC、上级 MOC和顶级知识地图。
5. 立即验证该批次；验证通过后再处理下一批。

优先使用可逆移动。不要执行模糊路径、未解析变量或宽泛递归删除。工作区已有修改时，只触碰本任务清单内的文件。

### 六、验证

完成后至少检查：

- 文件总数与迁移映射一致。
- Markdown Frontmatter 完整，`domain`、`status` 等字段合法。
- Wikilink、附件嵌入和 Markdown 相对路径可解析。
- MOC 与 Dataview 使用实际新路径。
- 没有完全重复文件、孤立笔记、空目录和残留旧路径引用。
- 权威文档唯一，多版本经验已经收敛。
- `git diff --check` 无空白错误。

若 Obsidian CLI 可用，再用 CLI 验证；不可用时使用文件系统扫描，并在报告中注明验证边界。

## 输出格式

审查模式输出：

1. 结论。
2. 现状指标。
3. 结构问题及证据。
4. 推荐目标目录树。
5. 迁移映射摘要。
6. 风险与暂不处理项。

整理或重构模式输出：

1. 已实现结果。
2. 关键结构变化。
3. 合并、归档和删除统计。
4. 验证结果。
5. 未处理项及原因。
