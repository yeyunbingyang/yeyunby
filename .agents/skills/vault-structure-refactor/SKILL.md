# Obsidian 知识库结构重构

把目录重构视为信息架构迁移，而不是批量移动文件。先识别内容的职责和边界，再设计结构、生成映射、执行迁移并验证引用。

## 模式选择

根据用户意图选择最小充分模式：

- **审查**：只读取和分析，输出问题、目标目录树与迁移建议，不修改内容。
- **整理**：保持主要架构不变，处理归类、命名、多版本、重复附件和 MOC。
- **重构**：重新设计目录树，迁移文件，修复链接并更新导航。

用户只说“看看目录”时使用审查模式；明确说“整理、实施、重构、执行”时进入整理或重构模式。大规模移动前先给出目标树和迁移映射；用户已明确授权实施时，不重复询问可从本地规则确定的事项。

若用户要求“自问自答”，完整列出每个关键问题、建议答案、依据和可调整项，把经用户同意的结论写入项目文档或架构决策记录；不要只在对话中保留决策。

## 规则优先级

按以下顺序解释冲突：

1. 用户当前指令。
2. 仓库 `AGENTS.md`。
3. 仓库的命名、Frontmatter、归档与 MOC 规则。
4. 本技能。
5. 通用 Obsidian 习惯。

不要套用其他知识库技能中写死的 vault 路径或英文命名规则。

## 工作流程

### 一、建立基线

1. 定位知识库根目录和目标范围。
2. 阅读 `AGENTS.md`、顶级 MOC、Frontmatter 规范及命名规则。
3. 运行 `scripts/inspect-vault-structure.ps1`，统计目录、扩展名、Markdown、附件、空目录、重复哈希、疑似多版本文档和版本化实验资产。版本化资产只作为审查线索，不能按文件名直接判定冗余。
4. 检查工作区状态，区分用户已有修改与本次修改，不覆盖无关变更。
5. 按 Markdown、JSON、图片、视频和其他文件分别记录数量与字节数；对不可再生成或大量移动的二进制资产记录排序后的相对路径与 SHA-256，并汇总为清单摘要。
6. 把范围外的已修改、未跟踪或子模块状态列为保护清单；后续暂存只能使用目标路径，不使用全仓库 `git add -A`。

### 二、完成需求审查

在设计目录前回答并记录：

1. 整理对象是知识主题、持续项目、一次性交付还是外部资源？
2. 哪些内容是操作规范、提示词、实验记录、过程资产、结构化数据、失败版本、最终交付物和历史归档？
3. 每类内容的唯一权威来源是什么？哪些只是导航、摘要或历史证据？
4. 失败记录是否包含失败现象、原因分析、修复方案、复验结果和版本链？
5. JSON 与 Markdown 中的本地路径以知识库根、项目根还是文件自身目录为基准？
6. 用户要求保留、合并、归档或删除什么？是否要求提交、合并或推送？

信息可从仓库和用户上下文确定时，给出建议答案并继续；只有会实质改变结果且无法安全推断的事项才暂停询问。

### 三、进行领域建模

先判断每个内容单元属于哪一种，不用单一目录规则处理所有文件：

| 类型 | 主要组织方式 | 判断依据 |
|---|---|---|
| 知识 | 领域 → 子主题 → 笔记 | 内容能长期复用，目录表达稳定主题 |
| 项目 | 项目 → 规范/记录/产出/数据 | 有目标、过程、版本、运行数据和交付物 |
| 资源 | 来源或资产类型 → 条目 | 主要保存外部材料、工具或素材 |
| 附件 | 跟随所属笔记或项目 | 不单独构成知识入口 |
| 归档 | 状态优先，目录辅助 | 已被替代但仍有审计或经验价值 |

识别主题重叠、粒度不一致、项目伪装成知识主题、附件侵入导航层和历史版本平行维护等问题。

### 四、设计目标结构

遵循以下原则：

- 一个文件只有一个物理归属，跨主题入口使用 Wikilink 或 MOC。
- 目录表达稳定边界；状态、平台、成熟度等易变维度放入 Frontmatter、标签或 Bases。
- MOC 只做链接、摘要和动态聚合，不承载长篇正文。
- 主题链接超过仓库阈值时拆分子 MOC；仓库没有阈值时，以 10 条作为审查点。
- 避免只有一个文件的无意义目录，也避免一个目录长期堆放几十个不同职责文件。
- 项目内部按实际内容选择主要组织轴，不要让同级项目或每个子案例复制一致目录。大型资产库可按生产职责组织，商品系统可按素材类别与工具组织，单角色项目可按角色和版本链组织，小型规范集合可保持扁平。
- 以下名称只是职责词汇表，不是必须套用的目录模板；只有内容数量、独立生命周期或检索需求足以支撑时才建目录：

```text
00-导航与说明/
01-操作规范/
02-提示词/
03-实验记录/
04-图片与视频资产/
05-JSON数据/
06-版本与失败记录/
07-最终交付物/
90-维护与数据/
99-归档/
```

- `04` 保存输入、过程和可复用媒体；`06` 保存未通过版本、标注、原因与修复证据；`07` 只保存通过验收的交付版本。不要把“最终”“失败”继续埋在通用附件目录中。
- 子案例优先沿用所属项目的主组织轴。除非一个案例已经形成独立规范、实验、数据和交付生命周期，否则不要为它复制一套 `00` 至 `99` 结构。
- 操作规范可以链接提示词和实验，但不得复制其完整权威内容。提示词、实验记录和失败记录必须能够通过版本或实验 ID 互相追溯。
- 附件命名和目录应能反推出所属项目或笔记。

输出目标目录树，并为每个新增、合并、改名或取消的目录写一句理由。

### 五、生成迁移映射

在移动前建立表格：

| 旧路径 | 新路径 | 动作 | 理由 | 引用影响 | 风险 |
|---|---|---|---|---|---|

动作只使用：保留、移动、改名、合并、归档、删除。删除必须有明确授权，并先确认内容已合并、文件为完全重复，或没有保留价值。

处理多版本时：

1. 确定权威文档。
2. 比较版本差异。
3. 把仍有效的经验合并进权威文档。
4. 有审计意义的旧版设为归档；无独立价值且用户授权时删除。
5. 修复所有对旧文件名和附件的引用。

### 六、执行迁移

按小批次执行，每批只处理一个主题或项目：

1. 创建目标目录和 MOC。
2. 合并文本，再移动或改名。
3. 更新 Frontmatter、Wikilink、Markdown 嵌入、JSON/脚本中的本地路径和 Dataview `FROM`。
4. 更新相关子 MOC、上级 MOC和顶级知识地图。
5. 立即验证该批次；验证通过后再处理下一批。

优先使用可逆移动。不要执行模糊路径、未解析变量或宽泛递归删除。工作区已有修改时，只触碰本任务清单内的文件。

路径改写前先声明解析语义：以 `./`、`../` 开头的路径通常相对当前文件；项目内部以职责目录开头的路径通常相对项目根；知识库绝对路径相对 vault 根。验证器必须采用同一语义，不能把所有引用一律拼接到仓库根。

每次移动必须同时处理实体文件和引用。禁止只创建目录与 README、却把旧图片、视频或 JSON 留在原目录。

### 七、验证与对账

完成后至少检查：

- 文件总数、分类数量和总字节数与迁移映射一致。
- 二进制资产迁移前后内容哈希集合一致；新增或允许修改的资产必须单独解释差异。
- Markdown Frontmatter 完整，`domain`、`status` 等字段合法。
- Wikilink、附件嵌入和 Markdown 相对路径可解析。
- MOC 与 Dataview 使用实际新路径。
- 没有完全重复文件、孤立笔记、空目录和残留旧路径引用。
- 权威文档唯一，多版本经验已经收敛。
- `git diff --check` 无空白错误。
- 当前目录不再存在旧职责目录；历史 ADR 中保留的旧路径要明确标注已被新决策取代。
- JSON 先全量语法解析，再跳过 HTTP(S) 等外部 URL 检查本地引用，不能把外链误报为断链。

若 Obsidian CLI 可用，再用 CLI 验证；不可用时使用文件系统扫描，并在报告中注明验证边界。

### 八、记录失败与解决方案

把迁移中的真实失败写入验证报告或失败记录，至少包含：操作、症状、根因、影响、解决方案和复验结果。区分真实数据问题与验证器误报，例如相对路径基准错误、外部 URL 被当成本地文件、Git 中文路径转义造成的范围误判。不要只写“已修复”。

### 九、Git 安全交付与最终审查

1. 在用户要求实施或仓库要求隔离时创建 `codex/` 前缀分支；记录起点提交。
2. 只暂存目标根目录，使用关闭路径转义后的文件清单复核提交范围。
3. 提交前运行完整验证与 `git diff --cached --check`。
4. 提交后按用户要求执行快进合并；除非用户明确要求，不推送远端。
5. 合并后重新检查：当前分支、HEAD、分支祖先关系、提交范围、文件/字节/哈希、引用和工作区保护清单。
6. 最终报告给出目录职责、迁移统计、验证数字、提交哈希、合并状态、未处理项及原因。

用户要求“完成后审查”时，审查是交付条件，不是可选总结。发现问题则先修复、复验并追加提交，再宣布完成。

## 输出格式

审查模式输出：

1. 结论。
2. 现状指标。
3. 结构问题及证据。
4. 推荐目标目录树。
5. 迁移映射摘要。
6. 风险与暂不处理项。

整理或重构模式输出：

1. 已实现结果。
2. 关键结构变化。
3. 合并、归档和删除统计。
4. 验证结果。
5. 未处理项及原因。
